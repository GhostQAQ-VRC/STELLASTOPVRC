Modular Avatar 衣服装上后不动或没反应的诊断：依次检查 Setup Outfit 执行、骨骼名匹配与 Apply On Play 勾选

Modular Avatar（MA）衣服装上后不动或完全没反应，绝大多数是三件事没做到位——没执行 Setup Outfit、骨骼名不匹配、或 Apply On Play 没勾选。

第一步检查 Setup Outfit 是否真的执行过：在 Unity 中对衣服执行右键菜单 Modular Avatar 下的 Setup Outfit，成功后衣服根上会出现 Merge Armature 组件；没有这个组件说明从未成功设置。

第二步检查骨骼名匹配：衣服的 Hips 等主要骨骼名需要能对应上素体的同名骨骼（例如衣服 Hips 名包含素体 Hips 名），名字对不上时合并会失败或错位。

第三步也是最高频原因（社区经验约 99%）：Apply On Play 没有勾选。检查路径是选中 Avatar 根对象 → VRC Avatar Descriptor → 勾选 Apply On Play。该开关不打开时，MA 在进入 Play 模式或上传时不会对 Avatar 做任何处理，所有组件自然全部无效。

补充验证手段：右键 Avatar → Modular Avatar → Manual bake avatar 可在不进 Play 模式的情况下直接生成烘焙结果，用来确认最终效果。

Modular Avatar 衣服穿模破洞的处理：Shape Changer 隐藏遮挡部位、PhysBone Blocker 挡动态穿模、Overdraw 半透明视图查看穿模程度

Modular Avatar（MA）场景下衣服穿模破洞有两类处理——静态遮挡用 Shape Changer 自动隐藏被遮住的身体，动态顶穿用 PhysBone Blocker 挡住物理骨骼影响；判断穿模严重程度则用 Unity Scene 视图的 Overdraw 半透明视图。

Shape Changer 是 Modular Avatar 的反应式组件，启用后可修改形态键值或直接删除多边形，常用于在衣服遮挡处把身体对应部位收进去，避免身体从领口、袖口等位置露出来。

PhysBone Blocker 是 VRChat 的组件，加在被顶穿的部位（如胸、腹部）后，可以阻止 PhysBone 在该区域推动骨骼，从而消除动态穿模。

查看穿模程度的方法：Unity 的 Scene 视图左上角着色（Shaded）下拉菜单中选择 Overdraw，场景会以半透明叠加方式渲染，穿模重叠越多的区域越明显，便于定位问题部位。

Modular Avatar 服装适配两问：调体型衣服不变形用 Blendshape Sync 同步形态键、鞋子陷进地板用 Floor Adjuster 调垂直位置

两个常见服装适配问题各有专用组件——体型联动靠 Blendshape Sync，贴地高度靠 Floor Adjuster，两者都是 Modular Avatar 的组件。

调体型时衣服不变形：身体的体型通常由形态键（Blendshape）驱动，衣服若带有同用途形态键但未被关联，就不会跟随。解决方法是在衣服上添加 Blendshape Sync 组件，建立身体形态键到衣服形态键的同步映射，之后拖动体型滑块时衣服会一起变形。

鞋子陷进地板：鞋类模型的原点或底部位置偏低时，穿上后会整体沉入地面。解决方法是添加 Floor Adjuster 组件，用它调整物件的垂直位置，使鞋底正好落在地面高度。

这两个组件都属于装衣服后的常规微调步骤，是玩家最高频提问的前几名。

Modular Avatar 物件开关化与验证：Object Toggle 做可切换发型菜单、Default 复选框即时预览、换装闪现裸体是 1 帧延迟保护

在 Modular Avatar（MA）中做可开关的发型或服饰，用 Object Toggle 组件把物件接入菜单；调试时点 Inspector 里 MA Menu Item 的 Default 复选框即可立刻在 Scene 视图看到物件出现或消失，不需要进 Play 模式；切换瞬间闪现裸体是正常的，Object Toggle 自带 1 帧延迟保护自动处理。

制作概要：为发型（或任何想开关的 GameObject）配置 Object Toggle，并通过 MA Menu Item 暴露成菜单项；多个互斥发型各自做成一个开关项，即可实现同时只显示一个。

快速验证技巧：点击 MA Menu Item 上的 Default 复选框，Scene 视图立即反映效果。这是官方教程 3 强调的做法，能在不进 Play 的情况下确认开关是否配对。

关于闪现：切换衣物时偶尔看到一瞬间的裸体不是配置错误——Object Toggle 的设计带 1 帧延迟保护，用于隐藏切换空档，属于 Modular Avatar 的自动行为（对应官方 Reaction Timing 机制），无需修复。

Modular Avatar 在 MMD 世界的四个高频疑问：表情不对找 World、MMD Layer Control 必须装在 layer 上、小组件失效是保护行为、总开关在 VRChat Settings 组件

MMD 世界相关的四类高频问题各有明确答案——表情不对找 World 不找 Avatar；Layer Control 装错位置就 build 失败；小组件失效多半是 Modular Avatar 在刻意保护你的配置；总开关藏在 VRChat Settings 组件里。

表情不对：在 MMD 世界跳舞时面部表情异常，社区经验是约 99% 由 World 自身的表情覆盖行为导致，不是你的 Avatar 配置问题，一般无需改动 Avatar。

build 失败：使用 MMD Layer Control 时如果构建报错，几乎都是安装位置错误——它必须装到 animator 的 layer 上，而不是装到 state 上。

小组件失效：自己做的开关或小组件进了 MMD 世界就不工作，默认这是 Modular Avatar 的保护行为（防止用户配置被 MMD 动画覆盖），很多时候这个默认恰恰是正确的；确需放开时用 MMD World Support 开关。

总开关位置：Modular Avatar 的 VRChat Settings 组件中提供 MMD World Support 复选框，控制是否让 Avatar 适配 MMD World 的行为。

以上机制对应 Modular Avatar 官方文档 General Behavior 下的 MMD World Workarounds 子页（relay layers、padding layers、MMD Layer Control），源页标注为完整覆盖。版本备注：对应源页 v1.2（2026-08-13 复核，MA 1.17.x 时点）的官方文档转述；证据级 official。

Modular Avatar 参数冲突防护三招：MA Parameters 勾 Internal 防冲突、Menu Item 自动参数取消 Saved 与 Synced、Sync Parameter Sequence 与 VRCFury Parameter Compressor 互斥

Modular Avatar 参数体系有三个关键规则——分发 Prefab 用 Internal 防冲突、临时参数取消 Saved 与 Synced、跨平台顺序问题用 Sync Parameter Sequence 且不得与 VRCFury Parameter Compressor 同时使用。

防参数冲突：自制 Prefab 若与其他作者组件可能同场使用，在 Prefab 内的 MA Parameters 组件上勾选 Internal，让参数以内部方式处理，避免与别人同名参数互相干扰。

不保存不同步：Menu Item 会在使用时自动创建参数名；若这个参数只是临时控制、不需要保存状态或网络同步，在该 Menu Item 上取消 Saved 和 Synced 两个复选框即可。

跨平台顺序：同一 Avatar 分别上传 PC 与 Android 后若出现参数顺序对不上，使用 Sync Parameter Sequence 组件固定参数顺序。注意硬性限制：它与 VRCFury Parameter Compressor 冲突，同一个项目里只能二选一。

版本备注：Sync Parameter Sequence 与 VRCFury Parameter Compressor 冲突的具体表现与适用版本范围在候选来源片段中未说明，引用时建议对照官方文档复核。

Modular Avatar 错误报告工具用法：Tools → Show Error Report 打开错误窗口，改完配置需重新 Build 或 Manual Bake 才会刷新

Modular Avatar（MA）的错误诊断入口是 Tools → Modular Avatar → Show Error Report；错误列表只在重新构建后刷新，改完配置必须重新 Build 一次才能确认错误是否消除。

打开错误窗口：在 Unity 顶部菜单依次点 Tools → Modular Avatar → Show Error Report，即可看到当前 Avatar 的构建错误与警告列表。

刷新机制：错误报告对应最近一次构建结果。修复配置后若错误仍然显示，不代表没修好，而是还没重新构建——两种方式任选其一：进入 Play 模式触发自动构建，或执行 Tools → Manual Bake Avatar 手动烘焙。构建完成后错误报告即更新。

建议的调试节奏：改一处配置 → Manual Bake → 看错误窗口清零，再继续下一处，避免多处同时修改后难以定位是哪一处引发错误。

VCC 添加 Modular Avatar 仓库报 Failed to add Repo 的处理：点 Cancel 并确认 bd_ 仓库已勾选（VCC 已知 bug）

VCC（VRChat Creator Companion）添加 Modular Avatar 仓库时弹出 Failed to add Repo 属于 VCC 已知 bug，点 Cancel 关掉即可，随后确认 bd_ 仓库已被勾选，不影响正常使用。

处理步骤：出现报错弹窗时点 Cancel；打开 VCC 的仓库设置页面，检查列表中是否有名为 bd_ 的仓库并确认其处于勾选状态；该仓库地址为 https://vpm.nadena.dev/vpm.json ，勾选后即可在项目管理中正常安装 Modular Avatar。

补充：官方推荐用 ALCOM 代替 VCC 管理 VPM 包（ALCOM 添加同一 bd_ 仓库即可），且安装预发布版本时官方明确要求必须使用 ALCOM，因为 VCC 的依赖解析存在 bug。

证据边界：Cancel + 核对勾选的处理步骤在本条来源片段内无官方原文直接引用，属社区速查表表述；同主题的官方口径另见本页「Failed to add Repo 根因」相关条目（official）。

学习 Modular Avatar 组件内部结构的方法：拆解官方 Samples 的 Fingerpen 与 Clap 示例 Prefab

想知道一个 Modular Avatar 小组件内部长什么样，最快的办法是拆 Modular Avatar 自带的官方 Samples，入门推荐 Fingerpen（手指笔）和 Clap（鼓掌）这两个例子。

做法：在项目中导入 Modular Avatar 的 Samples 后，把示例 Prefab 拖进场景，逐层展开层级树，观察它的组件搭配——例如 Object Toggle、MA Menu Item、MA Parameters、Merge Animator 是如何组合在一个小道具里的；看完删除即可，不影响自己的 Avatar。

价值：Samples 是官方维护的规范范例，能直观看到命名、层级、参数注册的惯例，是自己动手做 Prefab 前最好的参照物。

证据边界：本条为社区经验归纳（inferred），Samples 清单详见源页 §9.6。

Modular Avatar 衣服换色换材质：Material Swap 组件批量替换材质，配合 Quick Swap 一键切换与即时预览

衣服换颜色或换材质，用 Modular Avatar 的 Material Swap 组件做批量材质替换，配合 Quick Swap 可以一键切换并即时预览效果。

组件分工：Material Swap 属于 Modular Avatar 的反应式组件，启用时按预设映射批量替换单个或多个渲染器上的材质，适合一套衣服做多套配色的场景；Material Setter 则是逐槽位替换材质的姊妹组件，二者按粒度选用。

使用要点：先把各配色做成材质资产，在 Material Swap 里建立原材质到目标材质的映射，再把它接入菜单（如配合 Quick Swap 或 Menu Item），即可在游戏内作为独立选项切换。

Modular Avatar 衣服局部删除与顶点颜色清理：Mesh Cutter 配 By Mask Vertex Filter 删袖子等部位，Remove Vertex Color 加到 Avatar 根解决染色

两类网格级清理都由 Modular Avatar 组件在构建期完成——删局部用 Mesh Cutter（配 By Mask Vertex Filter 过滤），去顶点色用 Remove Vertex Color 且要加在 Avatar 根上。

删除衣物局部：给衣服对象添加 Mesh Cutter 组件，选择 By Mask Vertex Filter 作为顶点过滤方式，按遮罩圈出要删除的部分（例如长袖改为短袖时删掉袖段），构建时会自动删除或隐藏这些多边形，源模型文件保持不变。

清除顶点颜色：部分模型自带顶点色，会把头发等部位染出不期望的颜色。处理方法是给 Avatar 根对象添加 Remove Vertex Color 组件，构建时统一移除顶点色，恢复材质原本的颜色表现。

Modular Avatar 菜单归置与平台过滤：Menu Installer 指定 Install To 子菜单避免顶层混乱，Platform Filter 加 Include VRChat 让菜单只在 VRChat 出现

菜单混乱用 Menu Installer 指定安装位置解决，平台差异用 Platform Filter 解决，两者都是 Modular Avatar 的标准做法。

菜单归置：安装带菜单的小组件或 Prefab 时，Menu Installer 组件允许指定 Install To 目标子菜单，把它的菜单项放进你规划的分类（如服装、道具）而不是堆在顶层，多个组件共存时菜单依然整洁。

平台过滤：给只想在特定平台出现的对象（如菜单项）挂 Platform Filter，添加 Include VRChat 条件后，该项目只会保留在 VRChat 平台的构建中，Android 构建会自动排除，适合放仅 PC 可用的功能入口。

Modular Avatar 道具世界固定与缩放隔离：World Fixed Object 钉在世界且多实例只生成 1 个 constraint 不额外费性能，World Scale Object 不随 Avatar 缩放

World Fixed Object 把物件固定在世界坐标中不随 Avatar 移动，World Scale Object 让物件脱离 Avatar 的缩放影响；且 World Fixed Object 多个并存不额外费性能——无论几个都只生成 1 个 constraint。

World Fixed Object：适合做放在世界里的道具，例如放置后不跟随玩家移动的标记物。组件在构建期为整个 Avatar 生成一个共享约束，所有挂了该组件的物件复用它，所以添加多个不会产生多个约束的性能负担。

World Scale Object：当 Avatar 被整体缩放（如大人化或小孩化）时，挂了该组件的物件保持自身尺度，不跟着变大变小，适合手持道具、武器等对尺寸敏感的东西。

证据边界：「只生成 1 个 constraint」的实现细节未附官方出处，引用前建议以 Modular Avatar 官方 World Fixed Object 文档复核。

Modular Avatar Global Collider 的两种玩法与 6 个上限：Manual Remap 把手指 collider 移到嘴部模拟咬东西，跨 Avatar 碰撞他人 PhysBone

Modular Avatar 的 Global Collider 组件有两个典型用途——用 Manual Remap 把手指碰撞体挪到任意位置（经典用法是移到嘴里模拟咬东西），以及让自己的 PhysBone 能撞到别人的 PhysBone；使用时有全局 6 个的数量上限需要注意。

咬东西玩法：给手部配置 Global Collider 并启用 Manual Remap，把 collider 的映射目标改到头部或下巴附近的骨骼，运行时手指的碰撞体就会出现在嘴部，可以与食物道具交互。

双人物理碰撞：默认情况下各自的 PhysBone 只与本 Avatar 碰撞；通过 Global Collider 把自己的碰撞体公开后，就能与他人的 PhysBone 产生碰撞效果，适合互动舞蹈、打闹类玩法。

数量限制：全局 collider 有 6 个的上限（源页以警示标出），规划互动功能时要预留名额。证据边界：6 个上限的具体出处（VRChat 官方限制还是 Modular Avatar 文档规定）未在候选片段标明，建议复核官方文档。

Modular Avatar Visible Head Accessory 第一人称可见头发：组件用法及不可挂在 PhysBone 链子级的硬性限制

第一人称看不到自己的头发，用 Modular Avatar 的 Visible Head Accessory 组件解决；硬性限制是该组件所在的物件不能挂在 PhysBone 链的子级上。

背景：VRChat 出于视线遮挡考虑，第一人称视角会隐藏整个头部网格，头发作为头部子物件一并消失。Visible Head Accessory 在构建时把指定头部配件标记为第一人称可见，实现帽子、刘海在第一人称仍可见的效果。

使用约束：目标物件必须按常规层级挂在头部下方，不能塞进 PhysBone 链条（如发梢的物理骨子级），否则组件无法正确处理，第一人称依旧不可见。

Modular Avatar 整体比例调整：Move Independently 配合 Scale Adjuster，non-uniform 缩放必须用 Scale Adjuster，子对象联动由 Adjust child positions 控制

调整 Avatar 整体比例的正确组合是 Move Independently 加 Scale Adjuster；不等比缩放只能用 Scale Adjuster；子对象被连带移动时，取消 Adjust child positions 勾选即可。

整体放大缩小：选中 Avatar 后用 Move Independently 方式配合 Scale Adjuster 组件调整整体比例，避免直接拖 transform 缩放带来的骨骼与约束错乱。

不等比缩放：当 XYZ 三个轴需要不同倍率（如只拉高不拉宽）时，必须使用 Scale Adjuster——普通缩放工具在不等比情形下会让子物体产生剪切歪斜，Scale Adjuster 会在构建期做安全换算。

子对象联动控制：Scale Adjuster 默认会按比例调整子对象位置以维持形状；如果只想缩放对象本身、保持子对象原位，取消组件上的 Adjust child positions 复选框。

Modular Avatar Reactive 组件两条铁律：优先级由 Hierarchy 层级顺序决定（最低者赢），不要依赖精确反应时序（官方明确警告）

Modular Avatar 反应式（Reactive）组件有两条必须记住的规则——冲突时层级顺序最低的赢；时序上不要追求精确，官方明确警告不要依赖精确 timing。

优先级规则：当多个 Reactive 组件（如多个 Shape Changer、Object Toggle）试图控制同一个对象或形态键时，Hierarchy 中层级顺序最低（更靠后）的那个获胜。排布组件时把最终想要的效果放在更低层级即可稳定覆盖其他配置。

时序规则：反应式组件的生效通过构建期生成的动画实现，可能存在一帧级别的延迟。官方文档明确警告不要依赖精确的反应时间，因此在设计必须精确到某一帧切换的效果时应改用显式动画或其他方案，不要拿 Reactive 当帧级调度器。

证据边界：优先级规则的完整表述位于源页 §5.1，本条速查表仅一行概括；详解见后续「Reactive 组件通用规则」条目。

Modular Avatar Blendshape Sync 不支持链式同步：只支持 A→B 与 A→C 的星型映射，不能 A→B→C 接力（官方限制）

Modular Avatar 的 Blendshape Sync 只支持星型映射（一个源直接同步到多个目标），不支持链式接力——A 到 B、A 到 C 都可以，A 到 B 到 C 不行，这是官方明确的限制。

正确做法：让所有需要联动的物件都直接以同一个源（通常是身体的形态键）建立各自的 Blendshape Sync 映射，形成一对多的扇形结构。

错误做法：指望第一件衣服把形态键转发给第二件衣服。链式结构中的中间节点不会成为新的同步源，末端物件不会得到同步，表现为静默失效。

Modular Avatar Replace Object 的一对一约束：一个组件实例只能替换一个目标对象

Modular Avatar 的 Replace Object 用于把一个 GameObject 整体替换 Avatar 上的另一个对象（典型用途是用 Prefab 模型替换素体自带的头发或配饰），使用时注意一对一限制：一个组件实例只能服务一个替换目标。

正确用法：每需要替换一处，就在来源对象上添加一个 Replace Object 并指定一个目标；有多处替换需求时并列添加多个组件实例。

常见误用：试图用一个实例替换多个对象，或在替换链上叠加依赖——这类配置不会按预期工作，应拆分为多个一对一替换。

Modular Avatar Merge Animator 路径模式选择：Relative 相对当前对象、Absolute 绝对路径；Direct Blend Tree 强行对齐动画时长导致播放速度不对，改用 Merge Animator

Merge Animator 配置的核心两点——Path mode 按动画路径书写基准在 Relative 与 Absolute 之间二选一；发现动画播放速度不对，多半是误用了 Direct Blend Tree 的时长对齐特性，应改用 Merge Animator。

Path mode 选择：Relative 模式下动画里的路径相对于 Merge Animator 所挂的对象解析，适合组件自带、按相对结构制作的动画；Absolute 模式按 Avatar 根开始的绝对路径解析，适合针对固定骨架结构编写的动画。选错模式的表现是动画作用不到目标对象。

Direct Blend Tree 的坑：Direct Blend Tree 为了让各分支同步混合，会把所有参与的动画对齐到同一时长，短动画被拉长、长动画被压短，观感就是播放速度不对。需要原速播放时改用 Merge Animator 直接合并动画层。

禁用 Modular Avatar 约束自动转换：删除 Avatar 根上的 Convert Constraints 组件即可

Modular Avatar 的约束自动转换能力由 Avatar 根上的 Convert Constraints 组件承载；不需要该行为时，直接删除这个组件即可，无需改任何全局设置。

操作：在 Hierarchy 选中 Avatar 根对象，找到 Convert Constraints 组件，右键 Remove Component 删除。删除后 Modular Avatar 在构建期不再自动执行约束转换，场景中的约束保持原样。

适用场景：与其它也处理约束的工具链共存、或需要精确控制约束处理时机时，禁用自动转换可避免双重处理。

Modular Avatar 是什么：让拖入 Prefab 即完成换装成立的编译期组装工具，五大痛点与解法对照

Modular Avatar（MA）解决的核心问题是把换装从手工手术变成拖拽安装——拖一个衣服或组件 Prefab 到 Avatar 上，剩下的骨骼合并、参数注册、穿模处理、动画修正全部由 MA 在构建期自动完成。

五大痛点与解法对照：衣服要手动合并骨骼、动骨、菜单——拖入后右键 Setup Outfit 一键完成；多个小组件参数冲突——MA Parameters 自动重命名隔离；衣服影响别的部位（穿模）——Shape Changer 自动隐藏被遮挡的身体；不同玩家的骨骼名不一样——Merge Armature 智能匹配骨骼；装上衣服后表情或动画坏掉——Merge Animator 自动修正动画路径。

理解类比（社区说法）：MA 之于 Avatar 组件，就像包管理器之于软件包——每个下载的衣服或小组件自带说明书，MA 负责把所有说明书翻译并正确安装到你的 Avatar 上。

Modular Avatar 工作模型三阶段：编辑模式摆组件、编译时（Play 与上传）一次性翻译成最终 Avatar、运行时只跑产物——MA 组件不是运行时组件

Modular Avatar（MA）是编译期工具——编辑模式摆组件，进 Play 或上传时 MA 一次性把所有组件翻译成最终 Avatar，VRChat 里运行的只是产物；MA 组件本身不是运行时组件。

三阶段模型：编辑模式指你在 Unity 中的一切操作——摆放组件、配置参数、调整骨骼；编译时（Build Time）由进 Play 模式或上传 Avatar 触发，MA 读取所有组件配置并生成最终 Avatar（这一步也叫烘焙 bake）；运行时（Runtime）指编译产物在 VRChat 中运行，此时 MA 组件本身已不参与。

推论：因为工作全部发生在编译时，Avatar 运行性能不受 MA 组件数量影响（影响的是产物结构）；反过来，任何装了没效果的问题都应首先怀疑构建没有发生（如 Apply On Play 未勾选）或组件配置未被正确读取，而不是运行时逻辑出错。

Modular Avatar 三个核心组件：Merge Armature 管骨骼挂接、Merge Animator 管动画合并、MA Parameters 管参数注册，其余 20 多个组件都是它们的快捷方式

Modular Avatar 组件虽多，核心只有三个——Merge Armature 管骨骼挂接、Merge Animator 管动画合并、MA Parameters 管参数注册；其余 20 多个组件都是这三个核心的快捷方式或附加功能。

Merge Armature：把衣服的骨骼挂到素体上，凡是 Skinned Mesh 物件（衣服、头饰、尾巴等）都要经过它，Setup Outfit 快捷方式底层调用的就是它。

Merge Animator：把小组件自带的 Animator 动画合并到 Avatar 的动画控制器里，任何带动画的组件都依赖它。

MA Parameters：注册并按需重命名 Animator 参数，解决多组件参数命名冲突，凡是用到 Animator 参数的小组件都应通过它声明参数。

学习建议：先吃透这三个组件的心智模型，再按需查其余组件，可以把 20 多个组件的学习成本压缩成三大件加语法糖。

Modular Avatar 反应式组件核心思想：GameObject 启用即触发效果——Object Toggle 切对象、Shape Changer 改形态键、Material Setter 与 Material Swap 换材质、Mesh Cutter 删多边形

Modular Avatar 的反应式（Reactive）组件共同遵循一个思想——不写动画，让 GameObject 在启用时自动产生效果；五个常用组件分别是 Object Toggle、Shape Changer、Material Setter、Material Swap、Mesh Cutter。

组件效果对照：Object Toggle 启用时启用或禁用其他 GameObject；Shape Changer 修改形态键值或直接删除多边形；Material Setter 替换材质；Material Swap 批量替换材质；Mesh Cutter 删除或隐藏多边形。

自动工作的原理：这些组件响应三类触发信号——动画对 GameObject 激活状态的控制、其他 Object Toggle 的联动、菜单的选中状态。也就是说，无论状态变化来自菜单、动画还是另一个开关，反应式组件都会随之重新计算效果。

设计意义：用户只需要声明什么状态对应什么效果的映射，构建期由 Modular Avatar 生成相应的动画层，省去手写 Animation Clip 与 layer 的工作量。

Modular Avatar 五步问题诊断法：截图留证、查最简单原因、查 Setup Outfit、查骨骼名、Manual Bake 看最终结果

Modular Avatar 出问题时按五步诊断法排查——截图留证、查最简单原因、查 Setup Outfit、查骨骼名、Manual Bake 看最终结果；这套流程玩家自己也能独立执行。

步骤 1 截图保存：看到异常先拍照或截图，方便回溯与求助时提供现场。

步骤 2 检查最简单原因：组件根本没添加？拖的对象拖错了？没进 Play 模式就期待效果？三个低级原因排除掉再往下走。

步骤 3 检查 Setup Outfit：看 Outfit 根对象上有没有 Merge Armature 组件，没有说明设置从未成功。

步骤 4 检查骨骼名：核对衣服的 Hips 等主要骨骼名是否能对应素体骨骼名（如衣服 Hips 名包含素体 Hips 名）。

步骤 5 Manual Bake 终审：右键 Avatar → Modular Avatar → Manual bake avatar，直接查看构建产物，绕过 Play 模式的变量确认最终效果。

Setup Outfit 自动化机制：自动找 Armature、自动加 Merge Armature、自动处理 A-Pose/T-Pose 转换

Modular Avatar 的 Setup Outfit 是一条全自动流水线——右键衣服根对象选择 Modular Avatar → Setup Outfit 之后，它会自动完成三件事：①自动找到衣服层级里的 Armature（骨架）；②自动添加 Merge Armature 组件完成骨骼合并；③自动识别并处理 A-Pose/T-Pose 骨骼姿态差异。

这意味着使用者不需要理解骨骼合并、姿态转换这些高级概念的具体原理，Modular Avatar 已经把它们封装起来自动完成。教新手时也不必讲解为什么能自动，只需要说明它会自动帮你做好即可——这正是一键换装对新手友好的核心原因，也是官方教程 1 把它作为入门第一步的设计意图。

形态键联动效果在编辑器无法预览：用 Avatar 3.0 Emulator 或 Gesture Manager 在 Play 模式测试

Modular Avatar 的形态键联动效果（例如 Shape Changer 随开关缩放身体部位）在编辑器中无法直接预览，这是官方在 Warning 框中明确告知的限制；正确的验证方式是进入 Play 模式，配合 Avatar 3.0 Emulator 或 Gesture Manager 这类模拟工具测试。

这两个第三方工具可以在 Play 模式下模拟 VRChat 的菜单开关与表情状态，让你不上传模型就能看到联动效果。官方的处理方式值得学习：不隐藏限制，同时给出绕过限制的方法。

排查思路：如果你在 Scene 视图里发现形态键联动没有生效，先不要以为是配置错误——那是编辑器本来就不预览此类效果，应改用上述 Play 模式工具验证，而不是反复改动配置。

Modular Avatar 六教程学习路线：按需求选教程顺序，90% 玩家只需教程 1 加教程 3

Modular Avatar 官方六篇教程不必全学——90% 的玩家只需要教程 1（配置简单服装/换装）和教程 3（简单对象开关）两篇，其余教程等遇到具体问题再按需学习。

Modular Avatar 教学原则 1 Prefab-First：配置封装成单个 prefab 拖入即用，再拆解原理

教 Modular Avatar 的第一原则是 Prefab-First（prefab 优先）：所有教学 demo 都要先封装成单个 prefab，学员第一步只需把 prefab 拖进场景就能看到效果，而不是先研究组件参数。

推荐话术：「先别看里面有什么——你先拖进去看效果。看完效果我们再拆解它为什么有效。」先让学员体验成功，再拆解原理。

Modular Avatar 教学原则 2 抽象层透明：讲它替你做了什么，不展开内部实现公式

教 Modular Avatar 时要对学员保持抽象层透明：告诉他们组件是什么、会自动帮他们做什么，但不要展开内部实现。

依据：官方 Setup Outfit 会自动识别 Hips 骨骼、T-Pose/A-Pose 姿态和骨骼轴向，替用户隐藏了绝大部分机械性工作——官方设计意图就是让不懂绑定的新手也能完成换装。

反例警示：教 Bone Proxy 时塞进 50 行矩阵/四元数公式，学员会被直接劝退；这些数学细节对完成换装毫无必要。

推荐话术：「你不需要理解它怎么算的，你只需要知道它会自动帮你做。」演示时分两层：先展示这是什么（组件卡片），再用一句话概括它替你做了什么。

证据边界：教学原则为社区归纳（inferred）。

Modular Avatar 教学原则 3 兼容降级明示：讲清不装 Modular Avatar 时的替代方案（fallback）

教任何一个 Modular Avatar 组件时，都必须顺带讲清没有 MA 时怎么办，也就是兼容降级路径（fallback），不能默认人人必装 Modular Avatar。

依据：官方发布物区分两级支持——Compatible（不含 MA 组件、普通环境可用）与 Preset（含 MA 组件、需安装 MA），说明官方本身就考虑了无 MA 环境。

典型例子：Bone Proxy 与 Merge Armature 都能把对象挂接到素体骨骼，但没有 Modular Avatar 时只能用传统父级挂接思路替代；不讲清选择标准，学员会误以为安装 MA 是唯一出路。

反例警示：默认学员必装 MA、从不解释替代方案，学员换个没装 MA 的项目就束手无策。

推荐话术：「这个组件依赖 MA。没装 MA 的话，可以用父级挂接的方式替代。」

证据边界：教学原则为社区归纳（inferred）。

Modular Avatar 教学原则 4 命名约定优先：exact name matching 比模糊匹配可靠，衣服 Hips 名必须包含素体 Hips 名

使用 Modular Avatar 合并骨骼时，命名约定比事后补救更重要：官方文档明确说 exact name matching（精确名称匹配）比 fuzzy matching（模糊匹配）可靠，所以应在项目开始就统一命名规范。

具体规范：衣服侧的 Hips 骨骼名字必须包含素体 Hips 的名字，Armature 父级等关键层级同样按约定命名，让 Modular Avatar 能精确配对骨骼。

反例警示：让学员随意命名、指望模糊匹配救场，多次安装/换装之后匹配参数会越来越乱，出现骨骼错配且难以排查。

推荐话术：「Hips 骨骼必须包含你素体的 Hips 名——从一开始就这么做。」命名习惯在第一节课定型，后续所有换装都受益。

版本备注：精确匹配优于模糊匹配为官方口径（MA 1.x 文档时点）；教学展开部分为社区归纳。

反例警示：只讲顺利路径（happy path），学员踩坑后只能去 Discord 求助，对教程的信任会崩塌。

推荐话术：「在教你组件之前，先说 3 个会坑死你的点。」

Modular Avatar 验证三件套：Edit mode sync、Play mode、Manual Bake 逐步自检

Modular Avatar 官方提供三种验证/调试手段，教学时应让学员每做完一步就自检。

Modular Avatar Reactive 组件通用规则：Active 双条件判定、Hierarchy 下方优先、Invert 反转条件

Modular Avatar 的 Reactive 类组件（Object Toggle、Shape Changer 等）遵循三条通用规则：激活判定、冲突优先级、Invert 反转。

一、Active（激活）判定须同时满足两个条件：①组件所在 GameObject 自身及其所有父级在 Hierarchy 中都处于 active 状态；②如果组件位于某个 Menu Item（菜单项）同级或其子级，则该菜单项当前必须被选中。注意：菜单判定只统计第一层父菜单，更深层子菜单的选中状态会被忽略。

二、优先级：当多个 Reactive 组件对同一对象的效果冲突时，Hierarchy 层级中位置最下方（排序靠后）的那个组件胜出。

三、Invert（反转）：勾选后组件逻辑反转——在条件不满足时生效，可用于实现关闭某菜单项时才触发的效果。

排查 Reactive 不生效时按此顺序检查：先看对象与父级是否 active，再看菜单项是否被选中且层级深度是否只有一层父菜单，最后看是否有排在更下方的同功能组件覆盖了效果。

Modular Avatar Reaction 1 帧延迟机制：链式反应逐帧生效防止切换闪烁裸露

Modular Avatar 的 Reactive 反应带有 1 帧延迟，这是防止切换瞬间闪烁的核心机制，而非缺陷。

以 A→B→C 链式联动、A 被关掉为例，时序如下：

帧 发生什么
1 不发生任何事（A 的 disable 被延迟）
2 A 真正 disable（B 的 disable 被延迟）
3 B 和 C 同时 disable

设计原因：以脱外套为例，关掉外套必须等内衣先显形之后再发生；如果没有这 1 帧延迟，两层衣物在同一帧切换，中间就会出现 1 帧裸体闪烁。

版本提示：官方说明完整时序细节可能在未来版本变化，但 1 帧延迟这一核心特性是稳定的。排查开关切换异常时应首先想到这一机制，不要把正常的逐帧生效误判为故障。版本备注：MA 1.x 官方文档（未标明具体版本号）。

Modular Avatar Reaction Debugger 调试工具：打开方式与 Object state / Reaction section 两区域用法

Reaction Debugger 是 Modular Avatar 自带的高级调试工具，可以在不进入 VRChat 的情况下模拟各种开关与菜单状态，预演 Reactive 组件的行为。

打开方式有两种：①在 Hierarchy 中右键目标 GameObject，选择 Modular Avatar → Show Reaction Debugger；②在任意 Reactive 组件的 Inspector 上点击 Open reaction debugger 按钮。

窗口分两个区域：①Object state（对象状态区）——手动强制某个对象为 active/inactive，或强制某个菜单项被选中/取消选中，用来模拟玩家的操作；②Reaction section（反应区）——列出当前影响这个对象的所有 Reactive 组件及其触发条件，用来核对联动关系是否符合预期。

教学建议：让玩家养成进 Play 模式之前先用 Debugger 验证一遍的习惯，省得每次都要进 Play 模式反复等待。

Modular Avatar 一键换装四步流程：拖 prefab → Setup Outfit → 隐藏原衣服 → Play 验证

用 Modular Avatar 给 Avatar 换装的标准流程只要四步。这也是官方教程 1（配置简单服装）演示的完整过程，示例为把 Capettiya 的 Sailor Onepiece 连衣裙装到 Anon-chan 素体上。

步骤详解：

①拖衣服到 Avatar：把衣服 Prefab 从工程面板拖到场景里 Avatar 的子级。注意不要拆 Prefab（不要 unpack），保持 prefab 完整以便后续更新。

②右键 Setup Outfit：在 Hierarchy 中右键衣服根对象，选择 Modular Avatar → Setup Outfit，Modular Avatar 会自动添加 Merge Armature 组件完成骨骼合并。

③隐藏原衣服（可选）：如果 Avatar 自带衣服，关闭原衣服对象的可见性（教程中关闭的是 SailorOnepiece_Anon_PB），避免新旧两件同时显示。

④Play 模式验证：进入 Play 模式，衣服应该跟着素体一起动，说明骨骼合并成功。

装好后的衣服层级结构如下（Modular Avatar 已在衣服根对象上添加 Merge Armature）：

OutfitName (GameObject) ← MA 加了 Merge Armature
  └─ Armature (GameObject)
      └─ Hips (Bone, 名字要包含素体 Hips 名字)
          └─ Spine
              └─ ...

这是约 90% 玩家需要的全部换装知识，第一次教学就讲这套流程。

Merge Armature 骨骼合并三规则：同名共享、独有下挂、含组件保留

Modular Avatar 的 Merge Armature（含 Setup Outfit 自动添加的同款组件）在合并衣服与素体骨骼时执行三条智能规则：

①同名骨骼 → 共享素体骨骼：衣服上与素体同名的骨骼（如 Hips、Spine）不会重复创建，而是直接复用素体的对应骨骼，衣服顶点跟随素体骨骼运动；

②衣服独有骨骼 → 移到对应素体骨骼下：衣服特有的骨骼（如裙摆、飘带骨）会被移动挂接到素体骨架的对应位置之下，保留独立运动能力；

③含组件的骨骼 → 保留为单独对象：如果某根骨骼上挂了组件（如 PhysBone、Collider），合并时会把它保留为独立对象，避免组件丢失。

排查应用：换装出问题时按这三条规则逐一核对 Hierarchy——衣服完全不动查同名骨骼是否正确配对；裙摆飘带不动查独有骨骼挂接位置；PhysBone 失效查含组件骨骼是否被意外处理。

Blendshape Sync 用法：把素体形态键（胸围体型）同步到衣服的四步配置

换装后如果调整素体体型（如胸部大小、身体形状），衣服不会自动跟着变——需要在衣服上添加 Modular Avatar 的 Blendshape Sync 组件，把素体的形态键变化同步到衣服上。

操作步骤：①选中衣服上带 Mesh Renderer 的对象；②添加 Blendshape Sync 组件；③点 + 新增一条同步项，绑定素体上的形态键（胸部大小、身体形状等）与衣服上对应的形态键；④按需添加多条同步项覆盖所有相关形态键。

配置完成后同步是全自动的：之后无论怎么改素体的形态键，衣服都会跟着变形，始终贴合身体，不会再出现调了体型衣服却穿不进的错位。

该步骤通常在 Setup Outfit 完成换装之后进行，属于标准换装流程的收尾环节。

Modular Avatar 布料服装配置流程：Bone Proxy 挂 Collider 加 Blendshape Sync 同步裙装（以官方教程 2 Dress Lumi 为例）

带布料（Cloth）和多 Collider 的复杂服装，在标准换装流程之外还要多做两步：用 Bone Proxy 挂接 Collider、用 Blendshape Sync 同步形态键。

完整流程：

①拖入服装并执行 Setup Outfit（与普通换装相同的基础流程）；

②处理 Colliders：在 Hierarchy 中选中所有 Hips_Collider 之类的 Collider 对象，一次性批量添加 MA Bone Proxy 组件，把 Target 拖入素体的对应骨骼（如 Hips）；Attachment Mode 会自动变为 As child; keep position（作为子级、保持世界坐标位置）；

③对其余 Collider 重复同样的操作；

④用 Blendshape Sync 处理 Skirt（裙子）和 Tops（上衣）的形态键，使体型调整能同步到布料部件。

两个关键组件的作用：MA Bone Proxy 负责把对象挂接到素体的特定骨骼上并保持世界坐标；Blendshape Sync 负责同步身体形状相关的形态键。

新手提示：这是进阶内容，新手阶段通常不需要；只有遇到 Cloth 布料破洞、穿透等问题时再回来学。

Merge Animator 布料自动化与 Outfit Changer 冲突：可自动设置胸部形态键与关闭 Cloth，但两者不可混用

Modular Avatar 官方教程 2 提到一个可选的高级技巧——用 Merge Animator 自动化处理布料服装：通过动画直接把胸部放大形态键设为 100、bra_off 设为 100、并关闭 Cloth 组件，省去手动逐项调整。

硬性警告：这种自动化方式会和 Outfit Changer（换装器）冲突，两者不能混用，使用前必须谨慎评估。

建议：教程本身不强制使用这个高级选项。新手阶段直接跳过；遇到 Cloth 破洞等问题时先掌握 Bone Proxy 加 Blendshape Sync 的标准方案；只有在确定不需要 Outfit Changer 动态换装的前提下，才考虑引入 Merge Animator 自动化。

Modular Avatar Create Toggle 三步做物件开关：自动生成 Menu Item / Menu Installer / Object Toggle 三组件

给物件（如 Anon-chan 的连帽衫）做表情菜单开关，最快的路径是 Modular Avatar 的 Create Toggle 一键生成，共三步。

操作步骤：

①右键 Avatar → Modular Avatar → Create Toggle，MA 会自动创建一个带全套组件的新 GameObject；

②在这个新 GameObject 上：改名成易识别的名字（如 Hoodie）；在 Object Toggle 组件上点 +，拖入你要开关的目标对象；用勾选状态决定菜单选中时目标是启用还是禁用；

③测试：勾选 Menu Item 上的 Default 项，场景中应该能看到物件发生对应变化。

Create Toggle 自动生成的三个组件各司其职：MA Menu Item 定义菜单项本身；MA Menu Installer 把这个菜单项安装到 Avatar 的主菜单；MA Object Toggle 承担实际的开关逻辑。

教学定位：这是 100% 玩家第一个要学的功能，教学时直接教 Create Toggle 方案，不要先教手动组装方案。

Shape Changer 形态键联动防穿模六步配置：shrink 键归零加 Delete 模式删多边形加 Overdraw 验证（官方教程 4 核心场景）

开关鞋子时脚部穿模、袜子与脚之间出缝的问题，用 Modular Avatar 的 Shape Changer 做形态键联动解决——这是官方教程 4（高级开关/形态键联动）的核心场景。

问题背景：很多 Avatar 带 shrink 形态键（穿衣服时自动收缩身体部位），鞋子关闭后袜子和脚之间出现缝隙，就是因为两层都被各自的 shrink 形态键收缩了，手动逐个管理非常麻烦。

配置步骤：

①先观察问题：关闭鞋子，确认袜子和脚之间出现缝隙；

②找到两层各自的 shrink 形态键（素体 Anon_body 上的一个、Socks 袜子上的一个），全部重置为 0；

③在鞋子 GameObject 上添加 Shape Changer：绑定要缩的底层形态键，模式选 Delete——直接删除被遮盖的多边形，性能更好；

④在袜子 GameObject 上同样添加 Shape Changer；

⑤用 Scene 视图的 Overdraw 调试模式验证不再穿模；

⑥创建菜单子菜单，把开关项放进去供玩家使用。

注意：形态键联动效果在编辑器中无法直接预览，最终效果需进 Play 模式配合 Avatar 3.0 Emulator 或 Gesture Manager 确认。

Modular Avatar 同步参数必须在 Primary 平台全量声明，缺失即 Build 失败，且不兼容 VRCFury Parameter Compressor

Modular Avatar 做参数同步时，Primary 平台必须包含所有要同步的参数，缺任何一个都会导致 Build 直接失败。

具体要求：

  • Primary 平台必须完整声明所有需要同步的参数；
  • 存在缺失时 Build 阶段报错失败，不会静默跳过。

已知限制：该机制与 VRCFury Parameter Compressor 不兼容，两者不可同时使用；若已安装 VRCFury 的参数压缩功能，需要在两者之间二选一。

排查建议：遇到因参数导致的 Build 失败时，先核对 Primary 平台参数列表是否覆盖全部被引用的同步参数，再检查是否启用了 VRCFury Parameter Compressor。

Modular Avatar Convert Constraints 组件：编译时把 Unity Constraints 转换为 VRC Constraints 的性能优化

Modular Avatar 的 Convert Constraints 组件用于在编译时把 Unity Constraints 转换成 VRC Constraints，是一项性能优化措施。

使用方式：

  • 默认用法：把 Convert Constraints 组件安装到 Avatar 根对象上；
  • VRChat Auto Fix 会在需要时自动为 Avatar 添加该组件，通常无需手动配置。

原理与收益：VRC Constraints 的运行性能优于 Unity Constraints，经编译期转换后 Avatar 运行开销更低。

Modular Avatar Merge Armature 字段详解：Merge Target、Prefix/Suffix、Position Lock Mode、Avoid Name Collisions 与通用 prefab 禁忌

Merge Armature 用于把服装/饰品的骨架合并进 Avatar 目标骨骼，但它绑定的是设置时那一个 Avatar 的固定骨骼，官方明确不适合面向多种 Avatar 通用的 prefab，跨模型复用会骨骼错位。

Inspector 字段一览：

字段 类型 说明
Merge Target GameObject / path 拖入 Avatar 上对应的目标骨骼；内部以路径形式保存，保证 prefab 序列化后可恢复
Prefix / Suffix string 匹配骨骼时自动剥离的前后缀（通常 Setup Outfit 时自动设置）
Position Lock Mode enum Not locked / Base==>Target（单向）/ Base<==>Target（双向）；Setup Outfit 默认单向
Avoid Name Collisions bool 默认开启，为新增骨骼改名以避免与其他合并资产冲突
Reset Position to Base Avatar 按钮 + 3 子选项 Do It! 按钮，附 Also set rotation / Also set local scale / Adjust outfit overall scale to match base avatar

关键限制（官方原文）：

  • Merge Armature 不是为可通用于多种不同 Avatar 的 prefab 设计的（例如 finger-pen 类通用道具）；
  • 组件假设被绑定的骨骼不会移动，因此无法泛化到设置时所针对的 Avatar 之外；
  • 自 1.7.0 起支持嵌套合并（A→B→C），由 Modular Avatar 自动决定合并顺序。版本备注：嵌套合并特性要求 MA 1.7.0+。

常见误用（经验归纳）：把通用化 prefab 交给 Merge Armature 处理，换 Avatar 就骨骼错位；随手关闭 Avoid Name Collisions 导致与他人物资的骨骼名冲突；误以为 Reset Position 是一次性永久调整。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文。

Modular Avatar Merge Animator 字段详解：Layer Type、Path Mode、Layer Priority、Merge Mode 与 Write Defaults 匹配

Merge Animator 把指定的 AnimatorController 合并进 Avatar 的对应动画层，本质是追加而非替换；想让用户彻底替换某一层，应让其按传统方式在 Avatar Descriptor 中替换；多个组件对同一 Layer Type 使用 Replace 模式会直接报错。

Inspector 字段一览：

字段 类型 说明
Animator to merge AnimatorController 要合并的动画控制器
Layer Type enum 目标层：FX / Action / Base / Additive / Gesture
Path Mode enum Relative（以组件所在对象为路径根）/ Absolute（以 Avatar 根）
Relative Path Root GameObject Relative 模式下作为路径根的对象
Layer Priority int 数字越小越先应用；相同 priority 按 hierarchy 顺序
Merge Mode enum Add（追加）/ Replace Existing Animator（替换 Avatar Descriptor 上同层 animator）
Match Avatar Write Defaults bool 匹配 Avatar 的写默认值设置，避免 ON/OFF 混用
Delete attached animator bool Build 时移除临时 Animator 组件

关键限制（官方原文）：

  • Merge Animator 只向现有动画层追加内容，不会替换它们；需要最终用户完全替换某层时，更推荐让其在 Avatar Descriptor 里按传统方式替换；
  • 多个 Merge Animator 对同一 Layer Type 且均为 Replace 模式时会报错；
  • VRCAnimatorLayerControl 只支持引用同一 animator 内部的层：需保证其 Playable 字段与 Merge Animator 设置的层一致，Layer 字段填写目标层在该 animator 内的索引；
  • 部分 blend tree 类型不支持 Write Defaults OFF 场景的转换。

常见误用（经验归纳）：Absolute 模式下在 prefab 内用临时 Animator 录动画导致路径错位；想覆盖官方动画层却忘记切换 Replace Mode；humanoid 骨骼动画不受 Relative Path 影响，误去调整路径。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文。

Modular Avatar Parameters 字段详解：Parameter Type 五类、Saved/Synced 合并语义与 256 同步上限

Parameters 组件统一声明和管理参数：Animator Only 与 Prefix 类型不会加入 Expressions Parameters；勾选 Synced 会占用 VRChat 网络同步配额（上限共 256 个）；Saved 取最外层设置，多个非嵌套组件设置不一致时任一勾选 Saved 即生效保存。

Inspector 字段一览：

字段 类型 说明
Name string 参数名或 PhysBone prefix
Parameter Type enum Bool / Int / Float / Animator Only / Prefix
Change name to string 把本作用域内的引用重映射到外部名字
Auto rename bool 自动挑选未被占用的名字
Default Value 多种类型 Avatar 重置时使用的默认值
Override Animator Defaults bool 连带改写 Animator Controller 内的默认值
Saved bool 跨 Avatar 切换/重启保留取值
Synced bool 占用网络参数配额（VRChat 总共 256 个）

类型要点：

  • Animator Only 与 Prefix 不会加入 Expressions Parameters；
  • Prefix 用于 PhysBone / Raycast 链路的批量参数配置。

关键规则（官方原文）：

  • Saved 参数取最外层的 Saved 设置；多个非嵌套组件把 Saved 设成不同值时，只要其中任意一个设为保存，该参数就会被保存；
  • 多个非嵌套组件设置了不同的非空默认值时会显示警告，因为无法确定应采用哪一个。

例外：多个非嵌套组件设置了不同的非空默认值时会显示警告（无法确定采用哪个）；嵌套场景下以外层设置为准。

常见误用（经验归纳）：把所有 bool 一律勾 Synced，撞上 VRChat 256 个同步参数上限；忘开 Override Animator Defaults 导致重置不生效；prefab 间非嵌套地拆分参数引发重命名冲突。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文；256 为网络同步参数个数上限的原文表述。

Modular Avatar Object Toggle 字段与行为规则：Hierarchy 靠后者胜出、状态更新晚一帧、全部 inactive 回退原状态

Object Toggle 以自身所在 GameObject 作为控制对象，按条件批量开关 Target 列表中的物体；多个 Toggle 冲突时 hierarchy 顺序靠后者生效，且状态变化比控制时机晚一帧。

Inspector 字段一览：

字段 类型 说明
Target GameObject 列表 + bool 按 + 添加目标；勾选＝条件满足时目标 active=true，不勾选＝条件满足时目标 active=false
Invert condition bool 反转触发条件
控制对象 GameObject 组件自身所在的 GameObject 即为控制对象

关键行为规则（官方原文）：

  • 多个 Object Toggle 控制同一目标发生冲突时，hierarchy 中最后出现的那个优先生效；
  • Object Toggle 在控制对象更新后的一帧才更新受动物体；Toggle 自身被禁用时，目标物体的禁用也比平常晚一帧；
  • 当控制某目标的全部 Object Toggle 都处于 inactive 状态时，目标使用其原始状态；若还有其他动画在操纵该物体，则使用动画状态。

常见误用（经验归纳）：用 Object Toggle 反向控制同一个父级造成循环；不了解一帧延迟，快速连切时看到闪烁误以为故障；多 prefab 冲突时没检查 hierarchy 顺序而误判为 bug。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文。

Modular Avatar Shape Changer 字段与规则：Delete/Set 双模式、Threshold 阈值与「勿改动画驱动 blendshape」冲突禁忌

Shape Changer 对目标 SkinnedMeshRenderer 的 blendshape 执行 Delete（删除多边形）或 Set（设为指定值）两种操作；严禁用它修改同时被其他动画驱动的 blendshape，此类需求应改为对含 Shape Changer 的物体本身做开/关动画。

Inspector 字段一览：

字段 类型 说明
Target Renderer SkinnedMeshRenderer 要操作的目标网格（一般是身体）
Blendshape 列表 List 每条记录可选 Delete 或 Set 模式
Mode（每条 shape） enum Delete（删除多边形）/ Set（设为指定值）
Value（Set 模式下） float 目标 blendshape 值
Threshold float 判定顶点受 blendshape 影响的阈值，调小可让更多顶点被删除

关键规则（官方原文）：

  • 不要用本组件修改同时被其他动画驱动的 blendshape；应改为对包含 Shape Changer 组件的物体做开/关动画；
  • 多个 Shape Changer 同时操作同一 blendshape 时，hierarchy 中较低者一般获胜；
  • 无动画参与时 Delete 能真正减少实测多边形数（性能最优）；有动画参与时仍能完全隐藏，但不会减少多边形数。

常见误用（经验归纳）：拿 Shape Changer 去改被表情动画驱动的 blendshape，导致表情失效；Threshold 未调整导致隐藏不完全；混淆 Delete 与 Set 两种模式的用途。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文。

Modular Avatar Bone Proxy 字段与限制：Attachment Mode 选择及不适合服装合并的原因

Bone Proxy 把对象附着到指定的 humanoid 骨骼上（内部以 humanoid bone + 相对路径保存以便 prefab 序列化）；官方明确它不是用来配置服装的，服装合并应改用 Merge Armature。

Inspector 字段一览：

字段 类型 说明
Target GameObject / humanoid bone + path 目标骨骼；内部以 humanoid bone + 相对路径形式保存
Attachment Mode enum As child at root（位置旋转归零、保持世界 scale）/ As child keep world pose（保留世界坐标姿态）
Match Parent Scale bool 开启时 local scale 被调整为 (1,1,1)，用于目标骨骼父级被缩放的场景
Advanced 折叠区 手动调整 humanoid bone / relative path

附着模式细节（官方原文）：

  • 子选项允许仅保留 position 或 rotation 其中之一；
  • As child keep world pose 通常只对特定 Avatar 专用的 prefab 有用，不适合跨 Avatar 通用。

关键限制（官方原文）：Bone Proxy 不是为配置服装设计的，请改用 Merge Armature。

常见误用（经验归纳）：用 Bone Proxy 挂衣服（正确做法是 Merge Armature）；在非专用 prefab 上选 keep world pose，换 Avatar 后错位；忽略 Match Parent Scale，父骨骼被缩放时饰品变形。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文。

Modular Avatar Menu Item 字段与规则：菜单类型、Is Default 唯一性、未绑定无效规则与菜单满自动分页

Menu Item 定义一个表达式菜单项，菜单显示名直接取自所在 GameObject 的名字；未绑定到菜单树的 Menu Item 完全无效，必须通过子层级、Menu Installer 或 Menu Group 三者之一挂接；多个菜单项同时勾 Is Default 属于未定义行为。

Inspector 字段一览：

字段 类型 说明
Menu Item Name string 取自所在 GameObject 的名字（在 hierarchy 直接改名即可）
Menu Type enum Toggle / SubMenu 等
Icon Texture2D 菜单图标
Parameter string 关联的 Animator 参数名
Submenu Source enum Expressions Menu Asset（使用 VRC 菜单资产）/ Children（使用子级节点）
Source Object Override GameObject Children 模式下替换子节点来源
Is Default bool 是否默认启用；多个勾选＝行为未定义
Saved / Synced bool 参数为自动创建时显示

关键规则（官方原文）：

  • 子菜单条目数超过 VRC 菜单上限时，会自动创建 next 项进行分页；
  • 多个菜单项被设为 Is Default 时结果未定义，官方明言不要这样做；
  • 未绑定的菜单项没有任何效果，必须通过子层级 / Menu Installer / Menu Group 三选一绑定；
  • 参数名未在 MA Parameters 或 VRC Expressions Parameters 中声明时会被自动创建。

常见误用（经验归纳）：Menu Item 没绑到 Installer/Group，导致表情菜单里找不到该项；多个菜单项都勾 Is Default 造成行为不确定；改了 GameObject 名字却没意识到菜单显示名也随之改变。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文。

Modular Avatar Menu Installer 字段与规则：默认安装顶层、菜单满自动分页与自制子菜单需两个菜单资产

Menu Installer 把 prefab 自带的菜单安装到 Avatar 的动作菜单，默认安装在顶层；目标菜单装满时自动拆分成多页；要自制子菜单必须创建两个菜单资产——一个作为子菜单控件、一个作为内层菜单本体。

Inspector 字段一览：

字段 类型 说明
Disable bool 勾选后完全关闭本 prefab 的菜单安装
Install To Menu path 通过 Select Menu 双击选择目标子菜单；支持引用其它 Menu Installer 正在安装的子菜单以实现扩展
Menu to install VRCExpressionsMenu 在 Prefab Developer Options 标签下添加要追加的菜单
Menu sources 自动生成 附加 Menu Item / Menu Group 后自动生成菜单条目

关键规则（官方原文）：

  • 默认情况下，prefab 的菜单会安装到 Avatar 动作菜单的顶层；
  • 所选菜单装满时会自动拆分成多页（子菜单）；
  • 若想要自己的子菜单，需要创建两个菜单资产：一个用于子菜单控件，一个用于内层菜单本身。

常见误用（经验归纳）：把子菜单控件和内层菜单合并成一个资产，导致子菜单内容与控件重复或缺失；Select Menu 选错位置，把 prefab 菜单装进了错误的分组；误以为 Installer 会替换已有菜单，实际行为是追加。

证据边界：「常见误用」为原文标注的经验归纳（INFERENCE），非官方原文。

VCC 添加 Modular Avatar 仓库报 Failed to add Repo 的根因与三步处理（多为误报，点 Cancel 即可）

VCC 添加 Modular Avatar 仓库时弹出 Failed to add Repo，多数情况是 VCC 自身 bug 导致的误报——仓库其实已经添加成功；正确做法是点 Cancel 取消，然后到 Community Repositories 列表确认 bd_ 仓库已勾选，而不是反复重试。

症状：在 VCC 中添加 Modular Avatar 仓库时出现 Failed to add Repo 错误弹窗。

根因：VCC 已知 bug（官方原话：“due to a bug in the VCC”）。

正确处理三步：

  1. 点击 Cancel 取消错误弹窗；
  2. 查看左侧 Community Repositories 列表；
  3. 找到 bd_ 仓库并确认其 checkbox 已勾选——已勾选即代表添加成功，无需理会该报错。

兜底方案（列表中确实没有 bd_ 时）：

  • 重新添加仓库 URL：https://vpm.nadena.dev/vpm.json ；
  • 重启 VCC 再试；
  • 改用 ALCOM 替代 VCC（VCC 已知问题较多）。

要点提醒：这是一个反直觉但正确的操作——见到报错反而应当取消并不再重复添加；官方对此不掩饰工具缺陷，直接给出绕过方案。版本备注：对应官方 Dealing with problems/install 子页口径（源页 v1.2 复核时点）。

Modular Avatar 进 Play 完全不处理的最高频原因：Apply On Play 未勾选及六步修复

给 Avatar 加了 Modular Avatar 组件、点了 Setup Outfit 却毫无反应时，绝大多数情况是 VRC Avatar Descriptor 里的 Apply On Play 复选框没有勾选；勾上后进入 Play 模式，Modular Avatar 就会自动处理。

症状：做了加组件、Setup Outfit 等操作，但 Avatar 没有任何变化。

根因：Apply On Play 未勾选（官方收录的最高频问题）。

修复步骤（精确到字段）：

  1. 选中 Avatar 根 GameObject；
  2. 查看 Inspector 面板；
  3. 找到 VRC Avatar Descriptor 组件；
  4. 在该组件内找到 Apply On Play 复选框；
  5. 勾选它；
  6. 进入 Play 模式，Modular Avatar 自动完成处理。

补充：该问题出自官方 Dealing with problems 主页；若勾选后仍有异常，可用 Modular Avatar 错误报告窗口继续定位具体组件与字段。

Apply On Play 字段位置与教学话术：位于 Avatar 根的 VRC Avatar Descriptor 内，必须进 Play 模式触发

Modular Avatar 组件「装上没反应」的最常见原因是 VRC Avatar Descriptor 的 Apply On Play 字段未勾选：该字段不是独立组件，而是位于 Avatar 根 GameObject 上 VRC Avatar Descriptor 组件里的一个复选框，并且必须进入 Play 模式才会触发 Modular Avatar 的处理。

玩家教学要点：

  • 「99% 的情况」是友好教学表述，不要绝对化；
  • 指路要精确到「组件 + 字段名」，不要抽象地说「勾上那个选项」；
  • 玩家不需要理解背后原理，照做即可；
  • 不要向玩家解释「MA 在 Editor 不会自动处理」这类抽象信息。

可直接使用的教学话术：「装上组件没反应？99% 是没勾 Apply On Play。选中 Avatar 根（你素体最外层那个对象）→ 看右边 Inspector → 找 VRC Avatar Descriptor 组件 → 找里面那个 Apply On Play 复选框 → 勾上 → 进 Play 模式看看。」

ModularAvatarOutput 输出文件夹机制：单文件打包的原因与 Unpack 拆开的时机

ModularAvatarOutput 是 Modular Avatar 手动 Bake 后存放产物的专用文件夹，位置在 Assets/ModularAvatarOutput/。专门设置这个文件夹的原因有三点：避免 Unity 已知 bug、提升处理速度、保持工程文件整洁。

默认把所有生成资产打包成单个文件，原因是：多个散文件容易触发 Unity 导入 bug，打包后处理速度更快。

Unpack 按钮（选中文件 → Inspector → Unpack）的使用时机：

  • 想单独查看每个生成资源的形态；
  • 想用 git diff 等版本控制工具对比变化；
  • 调试单个组件的错误。

不需要这些操作时保持打包状态即可。

Modular Avatar MMD World 层禁用兼容机制：识别并禁用原 FX 层 2/3、relay layers 恢复、Merge Animator 层受 padding layers 保护

部分 MMD Worlds 在 VRChat 中会主动禁用 Avatar FX Animator Controller 的第 2 层和第 3 层，目的是禁掉表情、让 MMD World 接管表情控制——这是 VRChat MMD 圈子的约定行为。Modular Avatar 会自动处理以兼容这一行为，流程分五步：

步骤 MA 做什么 为什么
1 识别“原本是层 2、3”的层 这些层就是 MMD World 想禁的
2 让它们在 MMD World 中被禁用 满足 MMD World 的预期
3 如果新层插入到它们之前，添加 relay layers 中继层用于在 MMD World 之外时重新启用原 2、3 层（drive layers 2 and 3 off and on appropriately）
4 Merge Animator 添加的层不参与 由下述保护机制保证
5 必要时添加 padding layers 用来“垫”出位置，让 Merge Animator 的层落在非 2、3 的位置

保护机制（官方原话）：Layers added via Merge Animator (even in replace mode) will not be affected by this MMD world behavior; if necessary, padding layers will be added to protect them.

各情况是否受 MMD World 影响：

情况 是否受 MMD 影响 原因
原本在层 2、3 ✅ 是 MMD World 设计如此
Merge Animator 添加的层 ❌ 否 MA 主动保护
Merge Animator + Replace 模式 ❌ 否 即使 replace 也保护
手动添加到层 2、3 的层 ⚠️ 取决于手动管理 MA 不能自动管理手动添加的层

例外：手动添加到层 2、3 的层取决于手动管理，MA 的自动保护不覆盖这种情况。版本备注：层保护行为以所用版本的 Modular Avatar 官方文档为准。

Modular Avatar MMD Layer Control：把 Merge Animator 合并层主动 opt-in 进 MMD World 禁用范围，必须装在 layer 上

Merge Animator 合并的动画层默认不受 MMD World 影响；若希望某层在 MMD 播放时像素体原生层一样被禁用，需要主动 opt-in——把 Modular Avatar 的 MMD Layer Control（state machine behavior）直接加到目标层上。

行为对照：

  • 默认：Merge Animator 层完全不参与 MMD 控制，MMD World 只禁用素体原生层 2、3；
  • opt-in 后：加了 MMD Layer Control 的层会像原层 2、3 一样被 MMD World 禁用。

硬性限制：MMD Layer Control 必须直接安装到层上，不能安装到单个 state 上。官方原话：“Due to how state machine behaviors work, I can’t stop you from attaching them to individual states - but this will break your build (so don’t do that).”——装到 state 会破坏 build。

版本备注：MMD Layer Control 属较新特性，实际可用性以所用 Modular Avatar 版本为准（候选来源未标注具体版本号）。

Modular Avatar VRChat Settings 组件两步关闭 MMD World 支持：全局总闸与 MMD Layer Control 细粒度的关系

完全关闭 Modular Avatar 的 MMD World 支持只需两步——① 给 avatar 添加 VRChat Settings 组件；② 在组件里关闭 MMD World Support 设置。关闭后 Modular Avatar 不做任何 MMD 相关处理，avatar 在 MMD World 中的行为回到原生状态。

约束：VRChat Settings 组件在整个 avatar 上只能存在一个实例，但可以放在层级里的任意位置。

适用场景：玩家或创作者不希望 Modular Avatar 自动改写 MMD 相关层行为时，用此开关整体停用该机制，而不必逐层配置 MMD Layer Control。

与 MMD Layer Control 的关系：VRChat Settings 的 MMD World Support 开关是全局总闸——关闭后 Modular Avatar 不做任何 MMD 相关处理；MMD Layer Control 则是逐层 opt-in 的细粒度手段。两者分别对应『全量停用』与『单个合并层参与禁用』两种需求。

版本备注：该组件属较新特性，候选来源未标注具体 Modular Avatar 版本号，以所用版本文档为准。

Modular Avatar MMD 兼容边界：workaround 仅对禁用 FX 层 2 和 3 的世界有效，禁其他层的 MMD World 无法保护

Modular Avatar 的 MMD World 兼容方案有明确边界——只对『专门禁用层 2 & 3』的世界生效。如果某个 MMD World 禁用的是别的层（例如 4 & 5），Modular Avatar 无能为力，服装在该世界里仍会乱动。

原因：VRChat 当前 API 不支持通用方案。官方原话：“This workaround only works for worlds which specifically disable layers 2 & 3. Given current VRChat constraints, it’s not possible to provide a more general solution.” 这是平台限制，不是 Modular Avatar 的缺陷。

应对：玩家遇到此类世界时，可联系 World 作者反馈，或放弃在该 World 使用 MMD 集成；不应期待 Modular Avatar 侧修复。

版本备注：候选来源未标注具体 Modular Avatar 版本号，边界行为以所用版本文档为准。

分发含 Modular Avatar 的 Prefab：许可证允许夹带 MA 副本但官方强烈建议引导用户去 GitHub Releases 自行安装

发布含 Modular Avatar 组件的 Prefab 时，许可证虽然允许在包内夹带 MA 副本，但官方强烈建议不要这样做，而应引导用户前往 GitHub Releases（https://github.com/bdunderscore/modular-avatar/releases ）自行下载安装最新版 Modular Avatar。

  1. 用户可能装到很旧的 Modular Avatar 版本；
  2. 旧版可能把其他 Prefab 已装好的 Modular Avatar 降级、装坏；
  3. 多个 Prefab 各自带副本时容易出现版本错乱。

补充：作者计划提供 VCC-based 安装方式，但需等待 VCC 自身改进后落地。

性质界定：夹带 Modular Avatar 副本在许可证层面是被允许的，不构成违规；『引导用户去官方仓库』是基于版本管理可靠性的强烈建议（strongly recommend），而非许可条款的强制要求。版本备注：候选来源未标注具体版本号。

嵌套 Prefab 方案让同一服装同时兼容 Modular Avatar 用户与非 MA 用户：Create Base 四步流程与 Apply as Override 选择性同步

通过嵌套 Prefab 把『outfit 核心』和『MA 配置』分离，可以同时服务装了 Modular Avatar 和没装的两类用户：装了 Modular Avatar 的用户用原 prefab（带 MA 配置，拖入即完成）；没装的用户改用 base prefab（手动配置）。

  1. 正常创建 outfit prefab；
  2. 在 Project 视图双击 prefab 进入 prefab mode；

Modular Avatar 语义化版本策略：主版本破坏兼容、次版本向后兼容、补丁一般无影响，推荐同主版本内升到最新

主版本（1.x.x → 2.x.x） 不兼容变更 Prefab 必须更新才能继续使用

补丁（1.0.0 → 1.0.1） Bugfix（不破坏存档格式） 一般无影响，个别 bugfix 可能产生影响

Setup Outfit 工作机制四阶段：识别骨骼、T/A Pose 转换、创建 Merge Armature、创建 Mesh Settings

Setup Outfit 不是简单挂组件，而是按固定四阶段处理服装：

阶段 做什么 关键点
① 识别骨骼 找衣服的 Hips 骨骼 路径 OutfitRoot → [Armature] → Hips；Hips 名必须含素体 Hips 名
② T/A Pose 转换 旋转手臂对齐素体 手臂长度必须完全相同才能转换，否则跳过
③ 创建 Merge Armature 合并骨骼树 同名骨骼复用；含组件的骨骼不合并，移到对应素体骨骼下
④ 创建 Mesh Settings 配置渲染设置 Light Probe + Bounding Box 与素体保持一致

例外：手臂长度不一致时 T/A Pose 转换会被跳过（转换失败）。

排查指引：遇到『Setup Outfit 后衣服不跟随/位置不对』类问题时，按阶段顺序检查——先确认 Hips 是否被正确识别，再检查双方手臂长度是否一致，最后查看 Merge Armature 的骨骼归并与 Mesh Settings 是否正确生成。

版本备注：候选来源未标注具体 Modular Avatar 版本号。

Setup Outfit 骨骼命名规则：统一前后缀一致且大小写敏感，模糊匹配兜底可靠性差应避免依赖

Setup Outfit 依靠骨骼命名约定工作：衣服骨骼名应为『统一前缀 + 素体骨骼名 + 统一后缀』，所有骨骼的前后缀必须一致、大小写敏感；缺少统一前后缀的骨骼不会合并到素体。

命名相关事实：

  • Armature 对象名任意，Setup Outfit 不关心它叫什么（不强制叫 Armature）；
  • 骨骼轴向 X/Y/Z 任意组合均可，Merge Armature 自动处理。

模糊匹配模式（兜底）：当衣服骨骼名不规范时，Setup Outfit 会尝试重命名衣服骨骼以匹配素体。官方明确建议避免这种模式——可靠性差；最佳实践是从一开始就让衣服骨骼精确包含素体骨骼名。

智能行为补充：同名骨骼共享素体骨骼（不重复创建）；含组件（非 Transform）的骨骼不合并、移到对应素体骨骼下作为子级；素体没有的骨骼（如 Upper Chest）保留为独立骨骼；上半身存在特殊骨骼时自动用多个 Merge Armature 协同。

Bone Proxy 与 Merge Armature 选型对比：整树按名合并 vs 单对象按 Humanoid 角色绑定

Merge Armature 与 Bone Proxy 解决不同问题——前者合并整棵骨骼树，后者移动单个对象到指定骨骼。

维度 Merge Armature Bone Proxy
作用 合并整棵骨骼树 移动单个对象到指定骨骼
目标匹配方式 按骨骼名匹配 按 Humanoid 角色匹配（与骨骼名无关）
通用性 弱（依赖命名约定） 强（可适配任意 Avatar）
位置/旋转控制 自动 可选 snap / keep pose
整体开关联动 是（联动所有从 outfit scatter 出的对象） 否
典型场景 多骨骼服装（衣服、头饰、尾巴） 单点小物件（发卡、手持物）

核心区别：Bone Proxy 用 Humanoid 角色匹配，可制作跨 Avatar 通用的 Prefab；Merge Armature 智能合并骨骼树，用户的任何动画开关都能联动整组散落对象。

选型口诀：多骨骼服装用 Merge Armature，跨 Avatar 单点小物件用 Bone Proxy。

创作者避坑：PhysBone 残留在 Hips/Chest 等 humanoid 骨骼上会导致 Modular Avatar 行为不可预测

服装 Prefab 中残留在 humanoid 骨骼（Hips/Chest 等）上的 PhysBone 组件是高发雷区——这类组件多半是从素体复制时忘记删除的，Modular Avatar 会尝试删除它们，造成不可预测的行为。

避坑方法（二选一）：

  1. 确保 PhysBone 组件位于 Merge Armature 范围之外的 GameObject 上；
  2. 或者把 PhysBone 放在衣服独有的骨骼上（不与素体骨骼同名）。

自查时机：发布 Preset 前、或收到『穿上衣服物理表现异常』反馈时，优先检查衣服 Armature 内 humanoid 骨骼上是否挂着多余的 PhysBone 组件。

成因说明：这类残留多发生在以素体模型为基础改制服装时——PhysBone 组件随骨架被一并复制进衣服 Prefab，落在 Hips/Chest 等 humanoid 骨骼上未清理；Modular Avatar 构建时会试图删除它们，删除动作与其他处理的叠加使最终表现难以预测。

创作者避坑：衣服与素体的 Armature 和全部骨骼完全同名会触发 Unity bug，勿依赖 .1 后缀兜底

当衣服的 Armature GameObject 和全部骨骼都与素体完全同名时，会触发一个 Unity 已知 bug。Setup Outfit 有兜底机制——自动给 Armature 加 .1 后缀回避问题——但创作者不应依赖这条兜底路径。

正确做法：从一开始就修改衣服的 Armature 名或 Hips 名（例如加统一前缀），避免触发 bug 兜底逻辑。

关联提示：这与 Setup Outfit 骨骼命名规则一致——衣服骨骼名本就应带统一前缀/后缀以区分素体；完全同名既触发 Unity bug，也不符合命名预期。

自查方法：对照素体层级，逐一核对衣服 Armature 对象名与各骨骼名是否与素体完全相同；若完全相同，先重命名 Armature 或 Hips 再执行 Setup Outfit，不要依赖 .1 后缀兜底。

NDMF 生态执行顺序：优化工具先行、Fury 次之、Modular Avatar 收尾

多个 NDMF 工具共存时必须遵守固定执行顺序：先跑所有 NDMF 优化工具（AAO、Meshia 等），再跑 Fury，最后跑 Modular Avatar 与其他新内容 NDMF 工具——不按此顺序会出错。

原理：

  • NDMF 优化工具会修改 Mesh，必须发生在一切合并之前；
  • Fury 的换装逻辑需要先于 Modular Avatar 注入；
  • Modular Avatar 定位为『最后一棒』，负责把所有组件翻译成最终 Avatar。

执行链条速记：优化工具（AAO、Meshia 等）→ Fury → Modular Avatar；前两类处理都必须发生在 Modular Avatar 把组件翻译成最终 Avatar 之前。

排查指引：同时安装 AAO/Fury/Modular Avatar 时出现网格异常或换装失效，优先核对各工具的实际执行顺序是否符合上述链条。

Modular Avatar 创作者有三种递进式调试方法，建议按序使用：

Modular Avatar 服装创作者九步 SOP：从骨骼检查到版本发布的分发前标准流程

向他人分发 Modular Avatar 服装（Compatible 兼容衣装或 Preset 预设）之前，创作者应按以下九步 SOP 执行：

  1. 检查骨骼命名：层级需为 OutfitRoot → [任意名] → Hips，且该 Hips 名称包含素体的 Hips 名。
  2. 把服装拖到任意素体上执行 Setup Outfit，并进入 Play 模式验证。
  3. 检查 PhysBone：确保它不挂在 humanoid 骨骼上，必要时移到 Merge Armature 作用范围之外。
  4. 将 Armature 或 Hips 至少其中一个改名，以避开 Unity 的相关 bug。
  5. 决定本次作品做 Compatible 还是 Preset。
  6. 若做 Preset：添加 Blendshape Sync、Shape Changer、Object Toggle 与 Menu Installer 组件。
  7. Logo 决策：只有 Preset 可以使用 Logo，且必须按合规要求使用。
  8. 引导用户自行安装官方版 Modular Avatar，不要在自己的资源里夹带。
  9. 版本号遵守 Semantic Versioning（语义化版本），并用 Internal 参数防止参数冲突。

其中第 1、3、4 步分别针对骨骼命名规范、PhysBone 与 humanoid 骨骼冲突、Unity 已知重名 bug 三类高频问题，是发布前最容易出错、也最值得逐项核对的检查点。

NDMF 插件用 BeforePlugin 控制 Modular Avatar 前置构建步骤（含稳定性警告）

NDMF（Non-Destructive Modular Framework）允许开发者注册自定义构建插件，并用 BeforePlugin 精确控制自己的步骤相对 Modular Avatar 的执行顺序。最小可用示例（C#）：

[assembly: ExportsPlugin(typeof(MyPlugin))]
namespace nadena.dev.ndmf.sample
{
    public class MyPlugin : Plugin<MyPlugin>
    {
        protected override void Configure()
        {
            InPhase(BuildPhase.Generating)
                .BeforePlugin("nadena.dev.modular-avatar")
                .Run("Do something", ctx => { /* ... */ });
        }
    }
}

结构要点：程序集特性 ExportsPlugin 负责注册插件类型；插件类继承 Plugin 并覆写 Configure()；链式调用依次声明所属阶段 InPhase(BuildPhase.Generating)、相对排序 BeforePlugin 与实际步骤 Run(“Do something”, ctx => …)。若自定义逻辑必须发生在 Modular Avatar 处理之前，就以 BeforePlugin(“nadena.dev.modular-avatar”) 锚定顺序。

稳定性警告：NDMF 内部 API 不稳定；对 Modular Avatar 而言只有主版本插件标识 “nadena.dev.modular-avatar” 这一字符串是稳定的，不要依赖其内部实现细节。例外：确需依赖特定 pass 时到 GitHub 提 Feature Request 由作者评估增加稳定 API。

Resonite 构建 Dynamic Bones 转换规则：仅转换四类配置，其余参数按七种命名模板共享五项设置

把 Avatar 构建到 Resonite 时，物理骨骼会被自动转换。自动检测源有两种：Portable Dynamic Bones（NDMF 跨平台版）与 VRChat PhysBones；两者都会转换为 Resonite dynamic bones，且包含 colliders。

能带过去的配置项只有四类：exclusions（包括 Physbone Blocker 产生的排除）、colliders、collision radius、grabbability。其余大多数参数（如 Inertia、Stiffness 等）不做逐项转换。

替代机制是“命名 templates”分组：系统按骨骼名自动归类，模板名共七个——skirt、breast、hair、long_hair、ear、tail、generic。同一模板下的所有 dynamic bone 共享五项设置：Inertia、InertiaForce、Damping、Elasticity、Stiffness。

实践含义：想在 Resonite 上获得合理的裙摆/头发物理表现，重点不是逐骨调参，而是让骨骼命名命中正确的模板关键词，然后接受模板级的统一参数；原始 PhysBone 的精细逐骨差异在转换后不会保留。版本备注：官方文档时点快照，随 Modular Avatar 版本演进变化。

MA Settings Copier 跨 Avatar 版本复制设置：三步操作与两个前置条件

在 Resonite 中更新 Avatar 版本后，可用 MA Settings Copier 把旧 Avatar 上的设置搬到新 Avatar，避免重新逐项调参。它的复制范围是 Avatar Settings 槽下的所有子 Slot。

操作三步：

  1. 戴上旧 Avatar；
  2. 用激光拾取（laser pick）新的 Avatar；
  3. 打开右键菜单 → MA Settings Copier → Copy To Avatar。

两个前置条件缺一不可：其一，设置必须存放在 Avatar Settings 槽之下——放在其他位置的设置不会被识别和复制；其二，旧 Avatar 与新 Avatar 必须都已加载到 Resonite 中。排查“设置复制不过去”时，优先核对这两条。

Portable Avatar Components 定位与三组件最小可用配置（NDMFAvatarRoot / Viewpoint / Blendshape Visemes）

Portable Avatar Components（便携 Avatar 组件）是 NDMF 提供的一套不依赖具体平台 SDK（例如 VRCSDK）的 Avatar 组件体系，定位是支撑跨平台 Avatar 构建；它属于实验性功能，未来极可能以不兼容方式变更。

最小可用配置只需要三个组件：

  1. 在 Avatar 根对象上挂载 NDMFAvatarRoot（必需）；
  2. 在视点位置创建一个空 GameObject 并挂载 NDMF Viewpoint（推荐直接放在根下）；
  3. 如果 Avatar 的嘴型采用 Blendshape visemes，则挂载 NDMF Blendshape Visemes，并配置面部 mesh 与对应的 viseme blendshape。

例外：第三步仅在使用 Blendshape visemes 嘴型的 Avatar 上需要。

教学边界：99% 的玩家不需要 Portable Avatar Components——它是为“未来的跨平台 Avatar 工具链”打基础的实验性能力，除非学习者明确要开发跨平台工具，否则不建议现在教授或投入实际使用。版本备注：实验性（beta，未来可能不兼容变更）。

Portable Dynamic Bones 优先级规则与 settings template 机制：平台特定组件覆盖跨平台定义

Portable Dynamic Bones（便携动态骨骼）用于在不绑定特定 SDK 的前提下，把骨骼标记为需要物理模拟。设计上有三个特点：

  1. 只配置跨平台共有的最小属性集，不含平台专属参数；
  2. 具体物理行为由 settings template（设置模板）名称控制；
  3. 平台层可以在模板基础上做平台特定的配置覆盖。

优先级规则：当同一骨骼根 transform 上同时存在 portable 组件与平台特定的 dynamic bone 组件时，平台特定组件优先——平台专属定义会覆盖跨平台的最小定义。

成熟度警告：官方明确说明该组件“尚未完全可用”——现在能用，但未来极有可能以不兼容方式变更，不应把它当作稳定接口来依赖。版本备注：实验性（尚未完全可用）。

Fingerpen Prefab 层级拆解：Menu Installer/Parameters/Bone Proxy/Animator 组合与拖入即用的零配置设计承诺

Fingerpen（指间笔）Prefab 的内部层级大致如下：

Fingerpen  (根对象)
├── Armature（或直接挂 Mesh）
│   └── HandRef            ← 挂有 MA Bone Proxy 组件
│       └── PenMesh         ← 笔的 3D 模型

MA Menu Installer 的 Select Menu 五步操作与 VRChat 菜单格子上限背景

MA Menu Installer 组件负责把功能开关安装进 Avatar 菜单树，Select Menu 按钮就是“菜单装到哪”的开关。以 Fingerpen 为例的五步操作：

  1. 选中 Fingerpen 根对象，查看右侧 Inspector（Unity 右侧显示组件属性的面板）；
  2. 找到 MA Menu Installer 组件；
  3. 点击 Select Menu 按钮；
  4. 在弹出窗口中双击想把开关装进去的目标菜单（默认是 Avatar 顶级菜单）；
  5. 上传 VRChat 后，菜单里就会出现 “Fingerpen On/Off” 这样的开关项。

为什么需要手动选菜单：VRChat 玩家的菜单格子数量有上限（属于 256 参数限额的一部分）。Menu Installer 因此把安装位置的自主权交给用户——可以放进主菜单方便随手切换，也可以收进子菜单节省空间，灵活但不强制。

MA Bone Proxy 跨 Avatar 挂载机制：humanoid 骨骼引用自动转译与两种 Attachment Mode 取舍

MA Bone Proxy 赋予道具 Prefab avatar-agnostic（与具体 Avatar 无关）的挂载能力：无论是哪个 Avatar，只要有对应的手指骨骼，笔就会自动挂上去并跟随手指运动。Play 模式验证方法：进入 Play 后合拢 Avatar 右手手指，笔出现在指间并一起移动。

工作机制：Fingerpen 中名为 HandRef 的空对象是一个看不见的“挂载点”，其上的 MA Bone Proxy 组件把 Target 字段指向 Avatar 的右手手指骨骼；Modular Avatar 在编译（构建）时把这个挂载点重新连接到目标 Avatar 上对应的手指骨。

引用与转译细节：Bone Proxy 通过 humanoid 骨骼 + 相对路径引用目标；Prefab 保存时会自动完成引用转译，使同一引用在不同 Avatar 上都能正确解析。

Attachment Mode 二选一：As child at root——挂载物位置归零，适合做成通用 Prefab；As child keep world pose——保留世界位置，适合针对特定 Avatar 摆好姿态的场景。

Modular Avatar Fingerpen 手指笔样例五步安装流程：拖入 Avatar 子级、Select Menu 选菜单、Play 验证

Modular Avatar 官方示例 Fingerpen（手指笔）面向零 Unity 经验玩家，安装只需五步：准备工程、找到样例、拖入 Avatar、选菜单、Play 验证。

Step 1 准备：需要一个能进 Play 模式的 Avatar 工程；没有的话先按入门教程装好 Unity + VCC + Modular Avatar（MA）+ 一个测试 Avatar。

Step 2 拿到 Fingerpen：在 Project 窗口依次展开 Packages → Modular Avatar → Samples → Fingerpen；如果看不到，说明 Modular Avatar 没正确导入，需回头检查安装。

Step 3 拖上去：把 Fingerpen Prefab 拖到 Hierarchy 里 Avatar 的子级。注意不要拖到场景根目录，必须拖到 Avatar 里面。

Step 4 选菜单：选中 Fingerpen 根对象，在 Inspector 找到 MA Menu Installer 组件，点“Select Menu”后双击想用的菜单（默认即可）；看到 Selected Menu 字段显示菜单名即为成功。

Step 5 验证：点 Unity 上方 ▶ Play 按钮，在 Game 视图应能看到笔已经挂在手指上。这一步通过只代表 Prefab 内部没坏，上传 VRChat 前仍需继续完整验证。

VRChat Contact Receiver 接触接收器概念与拍手判定条件（门铃比喻：距离近且速度快才触发）

VRChat 的 Contact Receiver（接触接收器）是一种接收“接触事件”的组件；Modular Avatar 拍手样例（Clap）正是靠它把“双手快速合拢”这个物理动作变成音效和粒子的触发信号。

场景理解：在 VRChat 里把双手合拢时，Avatar 之间会发生“接触”，VRChat 系统能检测到这种接触事件（简单说：你的两只手“撞”到一起了）。Contact Receiver 就是用来接收这种接触事件的组件。

门铃比方：家里有门铃按钮（相当于 Contact Sender，按下去会响）和门铃接收器（相当于 Contact Receiver，听到响声就知道有人按）。拍手里两只手互相撞就是“按门铃”，拍手 Prefab 里的接收器听到响声后，就触发拍手音效和粒子。

拍手的判定条件：两只手的位置在空间里接近到一定距离，且接近的速度够快，才会被判定为“拍手”；缓慢合掌不会触发。

Clap 拍手样例 Prefab 内部结构：在 Fingerpen 全部组件上叠加 ContactReceiver、AudioSource 与 ParticleSystem

Clap（拍手）是 Modular Avatar 官方 Samples 中在 Fingerpen（手指笔）基础上叠加出来的进阶样例：保留 Fingerpen 的全部组件，额外增加了 ContactReceiver、AudioSource 和 ParticleSystem。

内部结构：

Clap  (根对象)
├── ... (和 Fingerpen 一样的所有组件)
├── ContactReceiver ← 多出来的！监听“拍手”事件
├── AudioSource     ← 拍手音效播放器
└── ParticleSystem  ← 拍手粒子效果

关键不同：Clap Prefab 里多了一个 MA Parameters 组件和多个 Contact Receiver，每个 Receiver 监听不同的身体接触组合（比如左手碰右手、左手碰头、右手碰头等），因此不同部位的碰撞都能汇入同一个“拍手”表现。

证据边界：结构图为教学示意，具体层级以实际导入的 Samples 为准。

MA Parameters 的 Internal 复选框防参数冲突机制：自动改名加内部引用同步，99% 场景都应勾选

Modular Avatar 的 MA Parameters 组件中，每个参数旁边都有一个 Internal 复选框；勾选后 Modular Avatar 会在生成 Avatar 时自动给参数改名（例如 On 变成 _On_internal_1 一类的内部名），并把组件内部引用同步到新名字，使该参数永远不会与其他组件冲突——绝大多数情况都应该勾上 Internal，这是 Modular Avatar 设计的“无脑安全默认”。

问题场景：装了 Clap，又装了一个别人做的“心跳特效”，两个组件都用同一个参数名 On。此时 VRChat 菜单系统会报错或行为异常——菜单里只有一个开关，却说不清控制的是哪个组件；Avatar 上存在两个叫 On 的参数，VRChat 不允许这样（参数限额 + 命名冲突）。

勾选与不勾的差异（以同时装 3 个都用 On 的小组件为例）：

同时装了 3 个小组件 没勾 Internal 时 都勾 Internal 时
Fingerpen（用 On） 3 个组件都往 VRChat 菜单塞 On 开关 MA 自动给每个 On 起不同内部名字
Clap（用 On） 菜单里只有 1 个 On 菜单里有 3 个独立开关
别人的发型切换（用 On） 按下去 3 个东西同时切换，一团乱 各自管各自的东西

对玩家的含义：不需要手动想参数名，不需要担心和别人组件打架，Modular Avatar 在编译时自动完成改名与引用同步。例外：只有“必须和其他组件共享同一个参数”时才不勾，这种情况极少见。

证据边界：参数自动改名的具体格式（_On_internal_1）为语料示意写法，实际生成名以 Modular Avatar 实际输出为准；Internal 复选框所属的 MA 版本范围语料未标注。

MMD 世界表情没被禁掉的五步诊断：核查 Avatar 是否真用 FX 层 2、3 做表情

玩家反馈「去 MMD 跳舞世界，表情没被禁掉，看着很怪」时，按以下五步诊断：

  1. 问玩家：是哪个 MMD World？不同 World 行为不同。
  2. 解释机制：这类 World 是通过禁用 FX 的层 2 和层 3 来禁表情的。
  3. 让玩家自查：Avatar 的层 2、3 是否用于表情控制？玩家不会查就教他“打开 Animator 窗口，看 FX 层 2 和 3 的名字”。
  4. 绝大多数情况（约 99%）：玩家根本没用层 2、3 做表情，所以 World 禁不掉——这不是玩家 Avatar 的故障。
  5. 解决方案：要么由 World 作者修复兼容，要么换一个 World。

例外：若玩家确实在层 2、3 放了表情控制但仍异常，则属 World 侧兼容问题，只能由 World 作者修复或更换 World。

注意事项：不要说「执行 MMD Layer Control」——绝大多数玩家不需要这个；也不要让玩家「加 MMD Layer Control」——玩家没在层 2、3 加东西，加了也没用。

MMD Layer Control 没效果或 build 失败的排查：组件误装到 state 而非 layer

玩家反馈「按教程加了 MMD Layer Control，没效果，还 build 失败」时，最常见原因是组件装错了位置——装到了 state（Animator 里的状态）而不是 layer（整个层）。

诊断与修复步骤：

  1. 让玩家截图组件在 Hierarchy／Animator 里的位置。
  2. 检查组件是不是装到了 state 上。
  3. 解释规则：必须直接装到 layer，不能装到层里面的 state。
  4. 修复：右键 layer 标题 → Add Behavior → MMD Layer Control。
  5. 重新 build。

教学比喻（可直接引用）：「layer 是大盒子，state 是盒子里的小球。你要把组件放到大盒子上，不是小球上。」

小组件动画在 MMD World 仍播放的原因：Modular Avatar 默认保护 Merge Animator 添加的层，属预期行为而非故障

玩家反馈「我装了个小组件，进 MMD World 它还在动」或相反「它的动画不播了」时，先确认组件的实现方式——这类小组件通常用 Merge Animator 制作。

机制说明：Modular Avatar 默认保护 Merge Animator 添加的层，不让 MMD World 禁用它们。所以小组件在 MMD World 里仍在运动，正是 Modular Avatar 在起保护作用，属于预期行为而非故障。

处理决策：

  • 希望它被 MMD World 禁掉 → 加 MMD Layer Control（必须装到 layer 上，不能装到 state 上）；
  • 不希望它被禁 → 什么都不用做，当前已经是正确状态。

教学关键句：“MA 帮你把你的小组件保护起来了。如果你想让它在 MMD World 被禁掉，加一个组件。”

手动构建动画器开关的官方完整步骤：Bone Proxy 加 Merge Animator 加 MA Parameters 加 Menu Installer（教学用途，日常优先 Object Toggle）

本教程为传统 Animator 方式做开关，官方定位是教学用途，实际做开关应优先使用 Object Toggle。官方原话：“You can also do this by building an animator manually, but why would you?”

完整步骤（官方标题写 6 步，实际划分为 Step 1-5 + Setup 6 + Finishing Up）：

Step 1：创建 GameObjects：ToggleDemo/HandRef/Cube；关键点：删除 Cube 的 Box Collider，否则会影响手部追踪。

Step 2：把 Cube 挂到手上：在 HandRef 上加 MA Bone Proxy，Target 设为右手骨头，Attachment Mode 设为 As child; at root；Bone Proxy 不需要放在顶层。

Step 3：创建 Animator Controller 和两个动画（CubeOff、CubeOn），添加 Any State 转换；使用 bool 参数 Cube，Transition Duration 设为 0，Can Transition to Self 关闭。

Step 4：加 MA Merge Animator，并同时加一个 Animator 组件；勾选 delete attached animator 和 match avatar write defaults；Animator 组件只是为了让 Unity 允许录制动画。

Step 5：加 MA Parameters（需点击 Show Prefab Developer Options 显示）→ 添加 Cube 参数 → Sync Mode 设为 Bool，勾选 Internal = true 以防止参数冲突。

Setup 6：创建 Expressions Menu 资产，加 MA Menu Installer 引用该 Menu（VRC 资产方式）。

Finishing Up：调整组件顺序（Menu Installer 放最上面）→ 拖到 Project 目录做成 Prefab → 拖到任何 Avatar 上都能使用。

例外提醒：Cube 若保留 Box Collider 会影响手部追踪，必须删除。版本备注：菜单路径以所用版本的官方文档为准。

MA Parameters 的 Internal 勾选项：自动隔离防参数名冲突，仅共享参数时取消勾选

Internal Checkbox 是手动动画器流程中最容易被忽略的选项。

勾选 Internal（推荐，绝大多数情况）：Modular Avatar 自动避免参数名冲突。官方原话：“If you set the internal checkbox, modular avatar will ensure that your Cube parameter doesn’t interfere with anything else on the avatar using the same parameter name.”（勾选 internal 后，Modular Avatar 会确保你的 Cube 参数不会干扰 Avatar 上其他使用同名参数的内容。）

不勾选 Internal：用户可以手动改名，使多个小组件能够共享同一参数，但代价是可能发生参数名冲突。例外：仅多个小组件需要共享同一个参数时才取消勾选并手动统一命名。

MA Parameters 位置约束：必须放在所有 Merge Animator 与 Menu Installer 的同一对象或共同父级上

MA Parameters 的位置约束（易错点）：它必须放在所有 Merge Animator 和 Menu Installer 的同一对象或父级上。

官方原话：“Make sure that MA Parameters is on either the same object, or a parent of all your Merge Animators and Menu Installers!”

违反此约束会导致这些组件找不到参数定义。

Merge Animator 流程中额外 Animator 组件的真实目的：仅为允许录制动画，构建时被 delete attached animator 自动删除

手动动画器流程要求在加 Modular Avatar 的 Merge Animator 的同时也加一个 Animator 组件，这不是功能需要，而是为了绕过 Unity 的限制——只有存在 Animator 组件时 Unity 才允许录制动画。

官方原话：“Adding an Animator here is also optional; we’re just using it so that Unity allows us to record animations. By checking the delete attached animator box, Modular Avatar will delete the Animator component at build time.”

结论：勾选 delete attached animator 后，这个辅助用的 Animator 组件会在构建（build）时被 Modular Avatar 自动删除，不影响最终 Avatar。

  • 适用人群：Object Toggle 适合所有玩家；手动 Animator 仅适合创作者；

官方建议：默认使用 Object Toggle；对手动构建动画器的评价是官方原话 “You can also do this by building an animator manually, but why would you?”（你也可以手动构建动画器，但你为什么要这么做呢？）。

边界说明：约九成玩家永远不需要学手动方式，但创作者必须理解它，因为某些复杂场景（复杂多状态机、多参数联动）必须使用 Animator。

证据边界：难度评级与“90% 玩家”比例为原文编辑性表述，非官方文档数据。

Merge Armature 组件总览：专为 Skinned Mesh 服装设计，三步配置与三种位置锁定模式

Merge Armature（必学组件）：把对象树合并到 Avatar 骨骼上，专为 Skinned Mesh 服装设计。

何时用：装衣服/头饰/尾巴；装任何 Skinned Mesh 配件。何时不该用：不用于“放个 Cube 在手上”（这种情况用 Bone Proxy）；不用于通用 Prefab（不同 Avatar 之间不能复用同一配置）。

关键功能：更新 SkinnedMeshRenderer 引用；最小化生成的骨骼数量；复用现有骨骼。

配置方法（3 步）：

  1. 组件加到源层级根对象；
  2. 拖入 Avatar 对应骨骼到 Merge Target；
  3. Prefix/Suffix 通常自动设置。

位置锁定模式（Position Lock Mode）：

  • Not locked——编辑模式下不跟随（几乎不用）；
  • Base → Target 单向——素体动、衣服跟随（默认，日常使用）；
  • Base ↔ Target 双向——互相跟随（高级场景，如摆动素体头发）。

Setup Outfit 自动化关联：自动查找衣服的 Hips 骨骼（名字需包含素体 Hips 名字）；处理 A-Pose/T-Pose 手臂位置转换；自动创建 Mesh Settings 组件。

版本备注：嵌套合并（A→B→C 自动决定顺序）自 MA 1.7.0 起支持。

Merge Armature 三个已知陷阱：素体骨骼上的 PhysBone、与素体完全同名的骨骼名、部分骨架失效

使用 Merge Armature 时需要提前规避的三个已知陷阱：

  1. 不要让 PhysBone 位于素体骨骼上（例如 Hips、Chest）——Modular Avatar 合并时会尝试删除这些 PhysBone，导致不可预测的结果；
  2. 避免使用与素体完全相同的骨骼名——这会触发 Unity bug；
  3. 对部分骨架（只有 Head 等单骨的情况）Merge Armature 会失效——此时应改用 Bone Proxy 替代。

例外：部分骨架场景的替代方案是 Bone Proxy。

Merge Animator 组件总览：把小组件 Animator 合并到 Avatar 指定层的四项关键功能与五步配置

Merge Animator：把小组件的 Animator 合并到 Avatar 的指定动画层。

关键功能：

  • 路径模式（Relative 相对路径 / Absolute 绝对路径）；
  • 层级优先级（控制多个合并的先后顺序）；
  • 合并模式（Add 追加 / Replace 替换）；
  • Write Defaults 匹配。

配置步骤：

  1. 组件加到 Prefab 对象上；
  2. 在 Animator to merge 中拖入 Animator Controller；
  3. Layer Type 选择目标层（FX、Action 等）；
  4. （推荐）勾选 delete attached animator；
  5. （推荐）勾选 match avatar write defaults。

Merge Animator 的 Write Defaults 自动匹配：检测 Avatar 的 WD 设置并对齐，混用 ON/OFF 会出 bug

Merge Animator 的 Write Defaults 匹配机制：勾选 match avatar write defaults 后，组件会自动检测 Avatar 当前使用 Write Defaults ON 还是 OFF，并自动调整被合并的动画器使之匹配。

原因：Write Defaults 设置混合使用会出现 bug，因此合并双方的 WD 状态必须一致，推荐交由此选项自动对齐。

Merge Animator 层优先级排序规则：数字小的先应用、相同按 Hierarchy 顺序；VRCAnimatorLayerControl 只能引用同一 Animator 内部层

Layer Priority（层优先级）规则：数字越小越先应用；数字越大越后应用（后应用的覆盖先应用的）；优先级数字相同时，按 Hierarchy 顺序处理。

两条限制：

  1. VRCAnimatorLayerControl 状态行为只能引用同一 Animator 内部的层，无法跨 Animator 引用；
  2. Merge Animator 默认不替换 Avatar 原有的 Animator 层；若需要替换，应使用 Replace 合并模式。

MA Parameters 五种参数类型：Bool / Int / Float / Animator Only / Prefix 及各自适用场景

MA Parameters 的参数类型一览：

  • Bool：布尔型，用于开关；
  • Int：整型，用于计数器；
  • Float：浮点型，用于滑块；
  • Animator Only：不加入 Expression Parameters，仅供动画器内部使用；
  • Prefix：作为参数前缀，用于 PhysBone/Raycast 场景，配置 PhysBone 链路时使用。

MA Parameters 重命名参数：Change name to 输入新名字即可，只影响组件外部引用，Auto rename 自动避让占用名

MA Parameters 的重命名功能：在 Change name to 字段输入新名字即可完成重命名。

作用范围：重命名只影响组件外部的引用。

便捷选项：勾选 Auto rename 后，Modular Avatar 会自动选择一个当前未被占用的名字，避免手工起名撞车。

MA Parameters 默认值回退顺序与 Saved/Synced 语义：Synced 占用 VRChat 参数限额共 256 个，建议用 Internal 节约

默认值规则：MA Parameters 设置的默认值在 Avatar 重置后生效；留空时回退使用 Expression Parameters 中的值，若无则为 0/false；勾选 Override Animator Defaults 可以覆盖 Animator Controller 里的默认值。

Saved 与 Synced：Saved 表示参数取值在跨 Avatar 更改和重启后仍然保存；Synced 表示参数进行网络同步——注意同步会消耗 VRChat 参数限额（总共 256 个）。

教学提示：参数限额很贵，建议玩家从一开始就使用 Internal 参数以节约限额。

口径说明：「VRChat 总共 256 个参数限额」沿用原文表述，未区分 bits 计数口径。

嵌套 MA Parameters：外层 Saved 与默认值优先于内层，内层重命名可被外层引用

嵌套使用 MA Parameters 时的优先级规则：外层的 Saved 设置和默认值优先于内层；内层执行的参数重命名可以被外层引用。

Object Toggle 组件基础用法：根据所在对象 Active 状态启用或禁用目标对象的三步配置

Object Toggle：根据所在对象的 Active 状态来启用/禁用其他对象，是做衣服脱穿、饰品开关的基础组件。

配置步骤：

  1. 把组件加到控制对象上；
  2. 点击 + 添加目标对象；
  3. 设置勾选状态：勾选 = 本对象启用时启用目标；不勾选 = 本对象启用时禁用目标。

多个 Object Toggle 控制同一对象的冲突裁决：Hierarchy 中最后者胜出，全部 inactive 则回到原状态或动画状态

Object Toggle 的冲突解决规则：当多个 Object Toggle 控制同一对象时，Hierarchy 中位置靠后（最后）的那个胜出；若所有相关组件都没有处于 active 状态，则目标对象维持其原始状态或动画状态。

Object Toggle 响应带 1 帧延迟防瞬时穿模：A→B→C 链式控制逐级累积延迟

Object Toggle 的响应时序：控制效果在 1 帧延迟后生效，这一设计用于防止切换瞬间的瞬时穿模。

链式影响：当控制链为 A→B→C 时，每经过一级就累积一帧延迟，因此长链条的末端响应会更慢。

Shape Changer 组件四步配置：Delete 删多边形性能好、Set 设指定值适配被动画影响的形态键

Shape Changer：根据 Active 状态修改形态键。

配置步骤：

  1. 组件加到要影响的对象上（通常是 SkinnedMeshRenderer）；
  2. 在 Target Renderer 拖入要修改的 Renderer；
  3. 点击 + 选择形态键；
  4. 选择模式：Delete 或 Set。

模式对比：Delete——直接删除对应多边形，性能好，适用于不会被动画使用的形态键；Set——把形态键设置为指定值，适用于会被其他动画影响的形态键。

Shape Changer 的 Threshold 阈值含义与多组件冲突裁决：调低阈值影响更多顶点，Hierarchy 最下方胜出

Threshold（阈值）：决定“哪些顶点算被影响”——降低阈值会影响的顶点更多，升高阈值则更少。

冲突规则：多个 Shape Changer 修改同一形态键时，Hierarchy 中最下方的组件胜出。

Bone Proxy 组件配置三步与 Attachment Mode 取舍：通用 Prefab 用 As child at root，Avatar 专用用 keep world pose

Bone Proxy：把对象挂到素体的特定骨骼上。

何时用：在手上挂个 Cube；在头上挂个发饰。何时不该用：挂整件衣服（应使用 Merge Armature）。

配置步骤：

  1. 组件加到要挂的对象上；
  2. Target 拖入目标骨骼；
  3. Attachment Mode 通常自动设置。

Attachment Mode 两种模式：

  • As child at root——位置/旋转归零，适合通用 Prefab（推荐）；
  • As child keep world pose——保留世界位置，适合 Avatar 专用 Prefab。

Match Parent Scale：启用后局部 scale 变为 (1,1,1)；关闭则保留原世界 scale；当目标骨骼自身带有缩放时，启用该选项更可靠。

例外：整件 Skinned Mesh 衣服不适用本组件，应改用 Merge Armature。

PhysBone Blocker 阻止父级 PhysBone 影响子对象：与 Bone Proxy 同对象配合实现饰品刚性附着

PhysBone Blocker：阻止父级 PhysBone 链影响子对象。

何时用：配件想刚性附着到 PhysBone 链上（如尾巴、耳朵上的装饰）。

与 Bone Proxy 的配合方式：

  1. 用 Bone Proxy 把对象挂到 PhysBone 链的某个骨骼上；
  2. 加上 PhysBone Blocker 后，父级 PhysBone 不再影响这个对象；
  3. 两个组件建议放在同一对象上，以确保刚性附着效果。

Menu Item 三种子菜单源与三种绑定方式：Children / Expressions Menu Asset / Source Object Override

MA Menu Item：在 Hierarchy 中定义菜单项，无需 VRC Expressions Menu 资产。

子菜单配置：

  • Submenu Source = Children——用子级对象作为菜单项；
  • Submenu Source = Expressions Menu Asset——使用 VRC 资产作为子菜单；
  • Source Object Override——指定其他对象作为子菜单源。

绑定方式（三种）：

  1. 作为另一个 Menu Item（Sub Menu 模式）的子对象；
  2. 与 MA Menu Installer 放在同一对象上；
  3. 作为 MA Menu Group 的子级。

Menu Item 未声明参数自动创建并可控制 Saved/Synced：多个 Is Default 会产生冲突

Menu Item 的自动参数创建机制：当 Menu Item 使用了未在 MA Parameters 中声明的参数名时，Modular Avatar 会自动创建该参数，并允许控制其 Saved/Synced 属性。

注意事项：多个菜单项同时声明 Is Default 会产生冲突，应保证同一参数只有一个默认项。

Menu Installer 安装规则：默认装到主菜单顶层、Select Menu 选目标、满员自动分页、Disable 完全禁用

MA Menu Installer：把菜单项安装到 Avatar 主菜单。

使用方法：

  • 默认安装到顶级菜单；
  • 点击 Select Menu 可以选择安装到的目标菜单；
  • 目标菜单位置满员时自动分页；
  • 勾选 Disable 可以完全禁用安装。

Prefab 开发者选项：

  • Menu to install——选择要安装的 Menu 资产；
  • Install To——安装到其他组件所提供的菜单。

Blendshape Sync 同步两个 Renderer 形态键的三条硬限制：不可链式、仅一级传递、不支持 Viseme/EyeLook 驱动

Blendshape Sync：把一个 Renderer 上的形态键值同步到另一个 Renderer。

何时用：让衣服的形态键跟随素体身体形状变化（如胸部大小调节）；在 Avatar 内不同 Mesh 之间同步形态键。

限制（三条）：

  1. 不能链式同步，A→B→C 的传递链不成立；
  2. 不支持通过多层传递，只支持一级；
  3. 运行时只支持 Animator 控制的形态键，不支持 Viseme/EyeLook 等系统驱动的形态键。

例外：Viseme/EyeLook 等系统驱动的形态键不在支持范围内。

Floor Adjuster 垂直位置调整与两条限制：VRChat 无法动态调高 Avatar，多个并存时不做任何调整

Floor Adjuster：调整 Avatar 的垂直位置，使鞋底对齐地板，典型场景是穿鞋子时避免陷进地板。

使用方法：

  1. 新建一个 GameObject 并添加 Floor Adjuster；
  2. 调整它的垂直位置对齐鞋底；
  3. 建议用侧视图/等距视图辅助对齐。

限制：

  • VRChat 本身不能动态调整 Avatar 高度；
  • 当 Avatar 上同时存在多个 Floor Adjuster 时，组件不做任何调整（无效配置）；
  • 此行为未来可能改变。

Platform Filter 平台过滤：Include 只在该平台存在、Exclude 在该平台移除，多数 MA 组件已内置处理勿重复设置

Platform Filter：按平台启用/禁用对象。

配置：

  • Include 模式——对象只在指定平台上存在；
  • Exclude 模式——对象在指定平台上被移除。

注意：很多 Modular Avatar 组件已经自动处理了平台限制（例如 Merge Animator 只对 VRChat 生效），这种情况下不要再重复设置 Platform Filter。例外提示：额外加 Platform Filter 于已内置平台处理的组件属于重复设置。

Visible Head Accessory 头部配件第一人称可见：原理是 VRCHeadChop，不可用于 PhysBone 子级、滥用会挡视线

Visible Head Accessory：让头部子对象在第一人称视角可见。

何时用：头发、配饰希望在第一人称可见，而不用照镜子确认。

限制：

  • 不能是 PhysBone 链的子级；
  • 如果把头部全部子级都设为可见，会遮挡自己的视线。

工作原理：利用 VRCHeadChop 让相关骨骼在第一人称保持可见；需要调整网格避免三角形穿过视角；可借助 proxy 骨骼和权重进行细化调整。

例外：PhysBone 链的子级对象不适用。

Replace Object 替换规则：一对一替换、双方子级保留、组件引用按同类型同索引修复、动画路径自动更新

Replace Object：完全替换 Avatar 上的某个对象。

何时用：替换 Avatar 的 PhysBones 配置；替换 Avatar 的 Body 网格。

限制：一个对象只能被另一个对象替换一次（限制了多组合并的可能性）。

子对象处理：替换对象的子级和原对象的子级都会保留，可以把配件装到替换对象之下。

组件引用修复：Modular Avatar 会尝试把旧对象上的组件引用修复为指向新对象，匹配规则是“同类型同索引”，没有模糊匹配。

对象命名：替换对象的名字可以与原对象不同，动画路径会自动更新为指向新对象。

例外：一个对象只能被替换一次，不支持多组合并。

Scale Adjuster 单独缩放单根骨骼不影响子级：仅对 Scale 工具生效，Adjust child positions 补偿子级位置

Scale Adjuster：单独调整某根骨骼的 X/Y/Z 缩放，不影响其子骨骼。

何时用：调整衣服以贴合非原设计的 Avatar；需要对 X/Y/Z 采用不同缩放比例的场合。

限制：只对 Unity 的 Scale 工具生效；组合工具（Move/Rotate/Scale 三合一）仍然会像普通缩放一样影响所有子级。

Adjust child positions 选项：调整子级的位置（而不是缩放）来补偿父级缩放带来的偏移。

例外：使用组合变换工具时该隔离效果不生效。

MMD Layer Control 背景机制：MMD World 禁 FX 第 2/3 层，MA 默认保护 Merge Animator 层，此组件使其可被禁用

背景：部分 MMD World 会禁用 FX 动画器的第 2、3 层，其原本目的是禁用表情动画；Modular Avatar 默认保护 Merge Animator 添加的层，使其不受 MMD 禁层行为影响。

MMD Layer Control 的用途：主动让 Merge Animator 添加的层参与 MMD World 的“禁用第 2、3 层”行为。

使用方式：把组件安装到目标层本身（作为 state machine behavior）；或者使用 VRChat Settings 组件完全禁用整个 MMD World 处理机制。

例外：不加此组件时，Merge Animator 的层默认被 Modular Avatar 保护、不受 MMD 禁层影响。

版本备注：来源未标注具体 Modular Avatar 版本号，MMD 相关功能属较新特性，版本敏感，以所用版本文档为准。

MMD Layer Control 安装位置硬限制：必须直接装在动画层上，装到单个 state 会破坏 build

MMD Layer Control 的安装位置限制：必须直接装到动画层（layer）上，不能装到单个 state 上——装到 state 会破坏 build。

官方原话：“I can’t stop you from attaching them to individual states - but this will break your build (so don’t do that)”（我没法阻止你把它们挂到单个 state 上——但这会毁掉你的构建，所以别这么做。）

原因：state machine behaviors 只有附加在 layer 上才有意义。

版本备注：来源未标注具体 Modular Avatar 版本号，以所用版本文档为准。

VRChat Settings 组件唯一性约束与 MMD World Support 总开关：开启自动处理、关闭完全禁用整套 MMD 机制

VRChat Settings 组件（MMD Layer Control 的关联组件）：

  • 唯一性：一个 Avatar 上只能有一个实例；

Material Setter 与 Material Swap 分工对比：单槽精确替换 vs 批量主题替换，Swap 支持 Quick Swap 快速预览

Material Setter 与 Material Swap 对比：

Material Setter——用法：把 Renderer 拖进去，修改指定的材质槽；适用：精确控制某个对象的材质。

Material Swap——用法：把 Material 拖进去，批量替换；适用：换衣服颜色主题这类大量替换场景。

Material Swap 高级功能：Quick Swap 模式可在编辑器内快速预览不同材质；支持 Same Folder / Adjacent Folders 两种素材范围；在 Inspector 中点箭头切换。

Mesh Cutter 四种 Vertex Filter：By Mask / By Axis / By Bone / By Blendshape 及效率原则与禁用场景

Mesh Cutter：按条件删除或隐藏多边形。

四种 Vertex Filter：

  • By Mask——用蒙版纹理指定区域，适合复杂形状；
  • By Axis——选取平面一侧，适合上下左右分割；
  • By Bone——按骨骼权重选取，适合身体/手部分割；
  • By Blendshape——选取形态键激活时会移动的顶点，适合做表情时删除。

效率提示：始终处于显示状态的部分，直接删除多边形以节省性能；有时会隐藏的部分，用隐藏方式处理（可能附加 constraint，占用性能）。

何时不该用：对象完全被其他网格盖住时，应改用 Object Toggle。

Global Collider 全局碰撞体：上限 6 个超出覆盖食指 Collider，Manual Remap 可手动指定占用项

Global Collider：让你的对象能够与其他 Avatar 的 PhysBone 互动。

何时用：配件想跟别人的头发互动；武器想被 PhysBone 抓住；把手部碰撞体移到嘴里模拟咬合。

限制：VRChat 全局碰撞体最多 6 个；超过 6 个时会覆盖食指的 Collider，因此要慎用。

Manual Remap：可以手动指定占用哪一个 Collider；注意 Head/Torso/Feet 只是 contact sender（接触发送器），不算物理碰撞。

例外：超过 6 个时食指 Collider 会被覆盖，影响指物交互。

World Fixed Object 世界固定与 World Scale Object 强制 scale=(1,1,1)：后者编辑器不预览进游戏才生效

两个世界相关组件对比：

World Fixed Object——用途：让对象跟随世界坐标、不跟随 Avatar 移动；适用：浮空剑、悬浮装饰等。

World Scale Object——用途：强制对象 scale 为 (1,1,1)，不受 Avatar 缩放影响；适用：复杂 constraint 道具。

注意事项：World Scale Object 的效果在编辑器中不预览，进入游戏后才生效。例外提醒：World Scale Object 的效果无法在编辑器预览，验证需实测。

Sync Parameter Sequence 五步流程：固定 PC 与 Android 参数顺序一致，Override Avatar 无需添加本组件

Sync Parameter Sequence（高级组件）：确保 PC 和 Android 版本的 Avatar 共享一致的参数顺序。

何时用：同一 Avatar 有多个平台版本；需要跨平台同步参数。

使用方法：

  1. 把组件加到 Avatar 的任意对象上；
  2. 选择 primary platform（即包含所有参数的版本）；
  3. 先在 primary 平台 Build & Upload；
  4. 再在其他平台 Build & Upload；
  5. Modular Avatar 自动同步参数顺序。

与 VRChat per-platform overrides 的关系：只在主 Avatar 上添加 Sync Parameter Sequence；Override Avatar 不需要添加，它会自动从主 Avatar 同步缺失的参数。
