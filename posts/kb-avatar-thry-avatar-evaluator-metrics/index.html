Thry Avatar Evaluator 7 项指标完整阈值 — VRAM/GrabPass/Blendshape/AnyState/Layer Count 五档界限与优化工作流

知识库 avatar

Thry Avatar Evaluator 全部指标阈值速查：VRAM(Texture/Mesh, PC/Quest)、GrabPass、Blendshape 三角形、AnyState、Layer Count 的 5 级界限

[COMMUNITY] Thry Avatar Evaluator（VRC-Avatar-Performance-Tools v1.3.7）检测 7 类关键指标并给出 Excellent/Good/Medium/Poor/VeryPoor 五档阈值：[FACT] VRAM Texture PC <40/<75/<110/<150/>=150 MiB；VRAM Texture Quest <10/<18/<25/<40/>=40 MiB；VRAM Mesh PC <20/<35/<55/<80/>=80 MiB；VRAM Mesh Quest <5/<10/<15/<25/>=25 MiB；Blendshape 影响三角形 <8000/<16000/<32000/<50000/>=50000；AnyState Transitions <50/<80/<100/<150/>=150；Animator Layer Count <12/<20/<30/<45/>=45 层。[FACT] GrabPass 采用简化分级：0 个=Excellent、1 个=Medium、>=2 个=VeryPoor。[COMMUNITY] 该工具是官方 Performance Rank 的补充：官方只检测面数/材质球数等基础指标，Thry 检测官方未覆盖或检测方式不同的指标，建议优化 Avatar 时两个工具同时运行。[UNKNOWN] 源文注记”AvatarEvaluator.cs 中只检测 1-7 项的前 4 项使用统一阈值”的表述含糊，无法确定哪些行共用同一阈值体系；GrabPass 分级缺少 Good/Poor 两档的明确定义。

Thry Evaluator VRAM 双套阈值常量：PC Texture 40/75/110/150、PC Mesh 20/35/55/80、Quest Texture 10/18/25/40、Quest Mesh 5/10/15/25 MiB

[FACT] Thry Evaluator 的 VRAM 阈值常量为双套：PC Texture Memory Excellent=40/Good=75/Medium=110/Poor=150 MiB；PC Mesh Memory Excellent=20/Good=35/Medium=55/Poor=80 MiB；Quest Texture Memory Excellent=10/Good=18/Medium=25/Poor=40 MiB；Quest Mesh Memory Excellent=5/Good=10/Medium=15/Poor=25 MiB。[FACT] 这些常量源码位置为 TextureVRAM.cs:38-57。

Thry VRAM 计算方式：Texture=Σ(width×height×bpp/8) 含 mipmap 链总倍数约 1.33；Mesh=Σ(vertexAttribute 字节×维度×顶点数)+BlendShape

[FACT] Thry VRAM 检测调用 TextureVRAM.QuickCalc(avatar)，累加所有 Texture（含 Material 的 TextureProperty 与 AnimationClip 的 Material Override）及所有 SkinnedMeshRenderer/MeshRenderer 的 sharedMesh，Tag 为 EditorOnly 的对象被跳过。[FACT] Texture VRAM 公式为 VRAM_texture = Σ_mipmap (width × height × bpp / 8)：Mipmap 0 为原图，Mipmap N 为 (width × height >> 2N) × bpp / 8，等比数列总倍数约 1.33。[FACT] Mesh VRAM 公式为 VRAM_mesh = Σ_vertexAttributes (byte × dimension × vertexCount) + blendShapeVRAM。[FACT] SkinnedMesh 的 Position/Normal/Tangent 各占 2 倍（同时存储未蒙皮与蒙皮后数据），BlendShape 每个受影响顶点额外 +40 字节。[UNKNOWN] 各顶点属性具体 bpp/字节数取值源文未逐项列出。

VRAM 优化建议：按 Alpha/NormalMap 选 BC7/DXT5 或 DXT1、>2048 纹理缩到 2K；多人场景 40 个 Avatar×150MB≈6GB 是硬性约束

[COMMUNITY] Thry 工具内置的 VRAM 优化提示（应作为常识记住）：从 1 米距离看 Avatar 逐步降低分辨率直到出现明显质量下降；有 Alpha/NormalMap 时选 BC7（8 bpp，质量高）或 DXT5（8 bpp，下载体积小），无 Alpha 时选 DXT1（4 bpp）；BC7 与 DXT5 的 VRAM 大小相同，差别仅在下载体积与质量；>2048 纹理一键缩小到 2K（质量损失很小）。[COMMUNITY] 工具硬编码的多 Avatar 累加示例：假设世界 VRAM 用量 2GB，40 个 Avatar × 150MB = 6GB（RTX 3070 8GB 几乎用完）；80 个 Avatar × 150MB = 12GB（超额，GPU 必须 swap 到系统内存）。[INFERENCE] 由此得出结论：Avatar VRAM 控制对多人场景至关重要。

GrabPass 检测：正则匹配 GrabPass{“Name”}（仅本地源文件）、阈值 0=Excellent/1=Medium/>=2=VeryPoor，且漏检无名称/#define/关键字触发及二进制 Shader

[FACT] Thry Evaluator 用正则 Regex.Match(File.ReadAllText(shaderPath), @“GrabPass\s*{\s*""(\w|_)+""\s*}”) 匹配 Shader 源文件中的 GrabPass { “TextureName” } 标准格式（来源 AvatarEvaluator.cs:436）。[FACT] 阈值分级来自 AvatarEvaluator.cs:41-42：0 个=Excellent、1 个=Medium、>=2 个=VeryPoor。[FACT] 检测盲点 4 项：检测不到无名称的 GrabPass {}；检测不到通过 #define 启用的 GrabPass；检测不到自定义 Shader 关键字触发的 GrabPass；仅适用于本地源文件 Shader，无法处理二进制 Shader。

GrabPass 性能成本：渲染点抓取整屏为纹理（4K RGBA32 约 33.18MiB 临时显存），折射/扭曲/描边等典型应用均有更优替代方案

[COMMUNITY] GrabPass 的原理是在某一渲染点抓取整个屏幕内容保存为纹理，供后续 Shader 采样。[FACT] 每次 GrabPass 的成本：CPU 端触发一次额外的 RenderTexture 分配；GPU 端把当前 framebuffer 重新拷贝一遍到显存。[INFERENCE] 分辨率成本按 4K RGBA32 估算一次 GrabPass 约占用 33.18 MiB 临时显存。[COMMUNITY] 典型应用（折射玻璃/水面、屏幕扭曲后处理、描边/Outline）几乎都有更好替代方案：折射玻璃用 RenderTexture+平面反射或 BoxProjection+Environment Reflection；屏幕扭曲用 PostProcess Volume+Shader Graph；描边用 Mesh 复制+缩放；实时反射用 Bakery Reflection Probe（预烘焙）。

Blendshape 影响三角形检测：统计有 BlendShape 的 SkinnedMeshRenderer 三角形总数并降序累加，阈值 8000/16000/32000/50000

[FACT] Thry Evaluator 检测 Blendshape 指标的方式（来源 AvatarEvaluator.cs:445）：获取所有 sharedMesh 非空且 blendShapeCount>0 的 SkinnedMeshRenderer，用 triangles.Length/3 计算三角数并降序排序，累加得到总三角形数。[FACT] 关键口径：统计的是有 BlendShape 的 SkinnedMeshRenderer 的三角形总数，不是 BlendShape 个数本身。[FACT] 阈值（AvatarEvaluator.cs:47-50）：<8000=Excellent、<16000=Good、<32000=Medium、<50000=Poor、>=50000=VeryPoor。

Blendshape 每帧开销原理：逐顶点计算 delta(pos/normal/tangent) 生成新 GPU buffer 并触发顶点 shader 重算，1 个 BlendShape×50,000 三角形=每帧 150,000 次运算

[COMMUNITY] Mesh 的 BlendShape 系统每帧执行：对每个 BlendShape 通道，计算每个顶点的偏移（delta position/normal/tangent），加到原始顶点上生成新的 GPU buffer，上传 GPU 后触发顶点 shader 重计算。[INFERENCE] 因此即使只有 1 个 BlendShape，如果作用在 50,000 三角形的 mesh 上，每帧都要处理 50,000 顶点 × 3（pos/normal/tangent）= 150,000 次运算，这是该指标昂贵的原因。

Blendshape 过重 Mesh 的拆分规则：>32,000 三角形触发 Error 警告，静态部分与带 BlendShape 动态部分拆分为两个 Mesh 可减少约 10 倍每帧处理量

[COMMUNITY] 工具对 >32,000 三角形的 Mesh 直接给出 Error 级警告，建议”将 mesh 拆分为多个 mesh，只让其中一个带 blendshapes，以减少受 blendshapes 影响的活跃多边形数量”。[INFERENCE] 标准做法示例：优化前 1 个 50,000 三角形 mesh + 10 个 BlendShape 每帧处理 500,000 顶点偏移；优化后拆为静态 mesh（45,000 三角形，无 BlendShape）+ 动态 mesh（5,000 三角形，10 个 BlendShape），每帧只处理 50,000 顶点偏移，约减少 10 倍。[COMMUNITY] 可用的工具：AAO（AvatarOptimizer）的 Merge Skinned Mesh / Remove Mesh in Box；Modular Avatar 不直接处理，可结合使用。

AnyState Transitions 检测：统计 base+special Animation Layers 下所有 anyStateTransitions 数量，阈值 50/80/100/150

[FACT] Thry Evaluator 检测 AnyState Transitions（来源 AvatarEvaluator.cs:428-429）：把 baseAnimationLayers 与 specialAnimationLayers 中的 animatorController 层展开，对每个层的 stateMachine.anyStateTransitions 计数求和。[FACT] 阈值（AvatarEvaluator.cs:43-46）：<50=Excellent、<80=Good、<100=Medium、<150=Poor、>=150=VeryPoor。

AnyState Transition 每帧对全部参数求值（贪婪匹配），健康上限约 50 个；基准显示数量本身影响不大，但”可以过渡到自身”带来 +20% 开销

[COMMUNITY] AnyState Transition 的核心问题是贪婪匹配：每个 AnyState Transition 都会对当前所有参数求值，即使条件不满足每帧都要检查；而 Normal Transition 只在源 State 激活时才检查，因此 AnyState 数量大会严重冲击 CPU 占用，健康上限约 50 个。[FACT] 基准测试（performance-benchmarks，JustSleightly）显示 AnyState 切换数量本身无显著影响，但启用”可以过渡到自身”（Can Transition To Self）会带来 +20% 开销。[INFERENCE] 示例：100 个 Toggle × 2 个 AnyState（开/关）= 200 个 AnyState，每帧检查 200 次条件；超过 100 个 AnyState 时累积效应会导致主线程占用增加等指标恶化。

减少 AnyState Transitions 的 3 种方法：合并条件用 Parameter Driver+总开关、MA Merge Animator 自动合并重叠 Layer、用 State 内 Trigger 替代 AnyState

[COMMUNITY] 减少 AnyState Transitions 的 3 种方法：其一合并条件——用 Animator Parameter Driver + 1 个总开关，替代”50 个 Toggle 各带 2 个 AnyState（On/Off）=100 个 AnyState”的结构；其二使用 Modular Avatar 的 Merge Animator，自动合并重叠 Layer，在减少 Layer 的同时减少 AnyState；其三用 State 内 Trigger Transition 替代 AnyState，因为 Trigger 只在该 State 激活时检查条件。

Animator Layer Count 检测：统计 baseAnimationLayers+specialAnimationLayers 总和，阈值 12/20/30/45 层

[FACT] Thry Evaluator 的 Layer Count 检测（来源 AvatarEvaluator.cs:443）：统计 baseAnimationLayers 与 specialAnimationLayers 的总和（_layerCount = layers.Count()）。[FACT] 阈值（AvatarEvaluator.cs:51-54）：<12=Excellent、<20=Good、<30=Medium、<45=Poor、>=45=VeryPoor。

Animator 每增加 1 层约 0.01ms 开销、主动频繁切换高 20-30%；45 层累积约 0.45-0.6ms/帧（90FPS 预算 4.1%-5.5%）

[COMMUNITY] Animator 运行在 CPU 上，每 Layer 每帧需要处理该层内所有 State、计算权重、混合 BlendTree、检查 Transition 条件，所以在 CPU 受限游戏（如 VRChat）中层数越少越好。[FACT] 基准测试（performance-benchmarks）给出：主动频繁切换比被动高 20-30%；每增加 1 层额外开销约 0.01 ms。[INFERENCE] 虽然单层便宜，但累积效应显著：45 层 × 0.01 ms = 0.45 ms/帧，占 90 FPS 预算的 4.1%；加上主动切换的 20-30% 增量约为 0.55-0.6 ms/帧。

减少 Animator Layer 的 3 种方法：MA Merge Animator 合并 Base/Additive/Gesture、1 个 Layer+BlendTree+Parameter Driver 替代每 Toggle 一 Layer、删除空 Layer

[COMMUNITY] 减少 Animator Layer 数量的 3 种方法：用 Modular Avatar 的 Merge Animator 把 Base/Additive/Gesture 合并到同一 Controller；用 1 个 Layer + BlendTree + Parameter Driver 替代”每个 Toggle 一个 Layer”的写法；用工具的 Empty States Check 提示找出并删除空 Layer。

Write Defaults 一致性规则：Animator 所有 State 必须同为 ON 或同为 OFF，工具以多数派为推荐并列出 outliers，Unity 2018+ 默认 Off 更安全

[COMMUNITY] Unity 需要 Animator 中所有 State 具有相同的 Write Defaults 值（全部 ON 或全部 OFF）：Animator 在 Layer 之间混合时用统一规则处理所有属性，不一致会导致属性在 State 切换时出现抖动/跳变。[COMMUNITY] ON 语义：State 退出时所有动画属性回到默认值，适合简单开关 Toggle，但跨 Layer 时容易把其他 Layer 控制的属性重置；OFF 语义：State 退出时属性保持当前值，适合复杂系统，不会重置其他 Layer 属性。[FACT] 工具检测算法（AvatarEvaluator.cs:431-434）以多数派为推荐设置、少数派列为 outliers（输出 LayerName/StateName 路径）。[COMMUNITY] 修复：在 Project Settings 统一默认值（Unity 2018+ 默认 Off 更安全），按列出的 State 路径逐个勾选/取消 Write Defaults，重跑工具确认。

Empty States 检查与修复：扫描 state.motion==null 的 State，成因是删 Motion 忘清理/导入丢失/MA 或 Fury 生成，修复用 0 长度空 AnimationClip 填槽

[FACT] Empty States Check（来源 AvatarEvaluator.cs:430）扫描所有 state.motion == null 的 State 并输出路径列表。[COMMUNITY] 常见成因 3 类：删除 Motion 后忘了清理 State；从其他工程导入的 Controller 引用了丢失的 AnimationClip；MA/Fury 等模块化组件生成空 State（尤其是使用 MA Merge Animator 时）。[COMMUNITY] 空 State 的风险：Unity 可能发出警告、可能影响 Layer Weight 计算、在 VRChat 上传时可能被 Performance Rank 误判（此点未量化）。[COMMUNITY] 修复：创建一个 0 长度的空 AnimationClip 拖到空 State 的 Motion 槽，重跑工具确认 outliers 为空；预防上用 Select > Missing Motion 过滤并检查 MA Merge Animator 的生成结果。

Thry Evaluator 优化工作流：先记录 Evaluator 6 项与 VRAM 明细，按 VeryPoor 决策树逐项处理，优化后确认全指标 ≤Medium 再跑官方 Performance Rank 上传

[COMMUNITY] Thry Evaluator 优化工作流分三段：优化前检测——选中 Avatar，右键 Thry/Avatar/Evaluator 记录 6 项指标当前等级与 outliers，再右键 Thry/Avatar/VRAM 记录每纹理/每 Mesh 的 VRAM 用量。[COMMUNITY] 决策树按顺序处理：Total VRAM VeryPoor → VRAM Checker 一键优化；Blendshape VeryPoor → AAO Remove Mesh in Box 或手动拆分 Mesh；AnyState VeryPoor → 重构 Animator（合并 Toggle / 用 Trigger）；Layer Count VeryPoor → MA Merge Animator；GrabPass VeryPoor → 替换 Shader（BoxProjection / Probe）。[COMMUNITY] 优化后验证：再次运行 Avatar Evaluator 确认所有指标 ≤ Medium，再运行官方 Performance Rank（SDK Build & Test），两者都通过后上传 VRChat。

Thry Evaluator 与官方 Performance Rank 对照：官方覆盖面数/材质球/材质内存/SMR/PhysBone 为上传门槛，Thry 独有 VRAM 分解/GrabPass/Blendshape/AnyState/Layer/Write Defaults/Empty States 为自检参考

[COMMUNITY] 与官方 Performance Rank 对照：官方检测面数、材质球数、材质内存（总 Texture）、Skinned Mesh Renderer 数、PhysBone 元件数，是 VRChat 上传的审核依据；[FACT] Thry Evaluator 独有检测 VRAM 详细分解、Mesh VRAM、GrabPass、Blendshape 三角形、AnyState Transitions、Layer Count、Write Defaults、Empty States。[COMMUNITY] 材质内存项官方检测总 Texture，Thry 不检测该项但 VRAM Checker 更细。[INFERENCE] 结论：Thry 工具是开发者自检工具（参考用），官方 Performance Rank 是上传门槛，两者互补，建议同时使用。
