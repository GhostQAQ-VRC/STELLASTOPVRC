Avatar 材质 Render Queue 渲染队列推荐取值范围表（不透明/镂空/透明/粒子）

Avatar 材质应按材质类型设置 Render Queue（渲染队列）数值，以获得正确的渲染顺序。推荐取值范围如下：

材质类型 推荐 Render Queue 说明
不透明(Opaque) 2000-2449 默认(Standard)
透明(Transparent) 2501-2999 标准透明(Geometry+ queue)
粒子 / 特效 3000+ Overlay 队列，最顶层渲染
Cutout 镂空 2450-2499 Alpha Test 队列(Unity 标准)

记忆要点：数值越大队列越靠后渲染；Cutout 镂空夹在不透明与透明之间（2450-2499），透明排在 2501-2999，粒子/特效使用 3000+ 的 Overlay 队列置于最顶层渲染。 【口径说明】Unity 内置渲染队列参考值为 AlphaTest 2450、Transparent 3000、Overlay 4000；本文采用社区约定口径：透明 2501-2999、粒子/特效 3000+。两套口径并存，与其他资料对照时注意区分。

Avatar 材质渲染异常诊断工作流与 lilAvatarUtils 批量检查验证方法

Avatar 出现材质消失、重叠、失焦等渲染异常时，按以下六步诊断工作流排查：

1. 发现 Avatar 材质异常(消失/重叠/失焦)
2. 选中异常材质 → Inspector → Shader Properties
3. 检查 Render Queue 字段
4. 与推荐范围对照（不透明 2000-2449、镂空 2450-2499、透明 2501-2999、粒子 3000+）
5. 修正 Render Queue 到推荐范围
6. 重新构建测试

工具辅助（lilAvatarUtils）：

  • Materials Tab：可一次性查看所有材质的 Render Queue
  • 修改方式：lilAvatarUtils 中可批量修改 + Apply 一次性应用
  • 验证方式：改完后用 lilAvatarUtils Lighting Tab 的 In Shadow / No Light 模式验证

Render Queue 常见误用后果与正确做法对照表

Render Queue 设置错误的典型误用与修正方法如下：

误用 后果 正确做法
把所有材质都设为 2450 强制前渲 擦除其他材质 透明用 2501，镂空用 2450
半透明用 Render Queue = 2000 与天空盒冲突 改为 2501
在 Particle System 用 Render Queue = 2450 遮挡问题 改用 3000+
复制 Shader 时不修改 Render Queue 渲染顺序错乱 按材质类型手动调整

核心原则：不要为图省事把所有材质统一到同一个队列值，应让每种材质类型落在各自推荐区间；复制 Shader 改作他用时务必核对 Render Queue 是否仍适配新用途。

VRChat 客户端 Dynamic Bone Limits 运行时限制系统（默认 32 Transforms / 8 Collision Checks，超限全部禁用）

除了上传时的 Performance Rank 评估，VRChat 客户端还有一套独立的运行时限制系统——用户端 Dynamic Bone Limits（2026-06-30 新增）：

  • 默认上限：Max Affected Transforms = 32，Max Collision Checks = 8
  • 超出后果：该 Avatar 的所有 Dynamic Bone + Collider 组件被禁用，且是全部禁用而非部分禁用
  • 配置位置：客户端 config.json，位于 %AppData%..\LocalLow\VRChat\vrchat\ 目录

因此即使 Avatar 上传时性能评级达标，运行时一旦超过这些默认限制，骨骼动态与碰撞仍会整体失效；做 PhysBone 优化时应同时控制受影响 Transform 数量与碰撞检查数量。

PhysBone 两种实装方式对比：直接建立在 Transform vs 收纳在空白物件内

PhysBone（简称 PB）有两种实装方式，各有优劣：

方式 优点 缺点
直接建立在 Transform 安装简单，不需指定 Root 管理困难，散布各处
建立在空白物件内 管理方便，可批量启用/停用 需手动指定 Root Transform

选择取决于更看重安装便捷还是后续批量管理（例如批量开关 PB 做优化对比时，空白物件内收纳方式更有利）。后续使用 AAO Merge PhysBone 合并时，两种方式分别对应不同的合并操作步骤。

AAO Merge PhysBone 合并条件（共同 Root 不超两级 + 数值完全一致）与抓取单边限制

使用 AAO Merge PhysBone 合并多个 PhysBone 时必须同时满足以下条件：

  1. 不同 PB 的上一级必须有共同 Root Transform（不可超过两级）
  2. 各 PB 的设定数值必须完全一致

已知限制：合并后抓取（Grab）只能抓一边，同时抓两边时会有一边没反应；摇晃与碰撞不受影响。

典型适用场景：左右对称的头发、耳朵等部件的 PB 设定通常一致，符合合并条件，可通过合并减少 PhysBone 组件数量以降低性能开销。

AAO Merge PhysBone 合并操作步骤：Transform 内与空白物件内两种场景

AAO Merge PhysBone 的合并操作按 PB 组织方式分两种场景：

场景一：合并步骤（Transform 内，PB 直接建在骨骼上时）

1. 展开 Armature，找到有相同设定的 PB
2. 在共同 Root Transform 上新建空白物件（如 Hair_Side）
3. 将左右 PB 拉入该物件层级
4. Add Component > AAO Merge PhysBone
5. 将左右 PB 拖入添加元素

场景二：合并步骤（空白物件内，PB 已收纳在空白物件中时）

1. 展开物件，检查所有 PB 的 Root Transform 位置
2. 找到可合并的 PB（如 Ear_L 和 Ear_R）
3. 新建空白物件（如 Ear），将 PB 拉入
4. Add Component > AAO Merge PhysBone
5. 拖入目标 PB

PhysBone 停用/删除判断方向与衣服 Collider 替换为 Avatar 本体碰撞器步骤

PhysBone 组件层面的精简有两个方向：

停用方向：

  • 会捏/拽但很少人用的 PB（如脸颊等）
  • 太小、移动幅度不明显的 PB

终极做法：如果某 PB 影响的物件关闭后不影响整体表现，直接删除该 PB。

碰撞器优化——大多数 Avatar 本身已内建完善 Collider，衣服自带的可以替换。替换步骤：

1. 固定 PB 的 Inspector
2. 找到 Avatar 本体相同位置的 Collider
3. 替换衣服自带的 Collider
4. 删除衣服自带 Collider 元件

AAO Merge Bone 骨头合并：作用、一举三得收益、融合间隔技巧与僵硬调整

AAO Merge Bone（骨头合并）的作用：将目标骨融合至上一级父骨，每合并一次减少一根骨。一举三得：

  1. 减少 Bones 数量
  2. 减少 PB 影响骨头数
  3. 避免设定 PhysBone Ignore 时末端不能动的问题

合并技巧（融合间隔选择）：上半部移动幅度小的保留，下半部移动幅度大的也保留。

僵硬调整：融合后若有 PhysBone，动态效果可能变僵硬；调整方法是降低 Pull、Momentum、Immobile。

Avatar 布料物理选型：Cloth 与 PhysBones 在物理模型、性能开销与适用场景上的五维对比

结论：链状结构的摆动物体（头发、尾巴、绳子）优先用 PhysBones，裙摆、长袍、披风等大面积连续布料才考虑 Cloth；性能敏感的 Avatar 默认选 PhysBones，因为 Cloth 的每帧布料计算开销明显更高。 两者在五个维度上的对比：

  1. 物理模型：Cloth 基于物理面料模拟（有限元方法）；PhysBones 基于骨骼链，使用 Verlet 积分逐级解算摆动。
  2. 性能：Cloth 开销重，每一帧都要进行布料计算；PhysBones 开销轻，只需解算骨骼链。
  3. 必要条件：Cloth 必须搭配 Skinned Mesh Renderer 才能工作；PhysBones 没有前置条件。
  4. 网格要求：Cloth 的网格必须单层、经过缝合、由四边形面片构成；PhysBones 对网格没有任何特殊要求。
  5. 适用场景：Cloth 适合裙摆、长袍、披风等连续面料；PhysBones 适合头发、尾巴、绳子等链状物体。 选型建议：只要骨骼链摆动能满足表现需求就用 PhysBones；只有在需要布料贴合、飘动等面料级效果时才引入 Cloth，并同步评估其对性能预算的占用。

Unity Cloth 使用必要条件：必须搭配 Skinned Mesh Renderer 且网格需单层、缝合、四边形

结论：使用 Unity Cloth 有两个硬性前提：物体必须搭配 Skinned Mesh Renderer（蒙皮网格渲染器），且网格本身必须满足单层、缝合、四边形三项拓扑要求；不满足时要么被 Unity 强制转换，要么布料模拟无法正常工作。 具体要求：

  1. Skinned Mesh Renderer：Cloth 组件建立在蒙皮网格之上；普通非蒙皮物体直接加 Cloth 时，Unity 会自动把它转换为 Skinned Mesh Renderer 再继续。
  2. 单层网格：参与布料模拟的网格应为单层面片，而不是带厚度的双层壳体。
  3. 缝合：布料网格的接缝处需要做缝合（焊接）处理，保证顶点连续。
  4. 四边形面片：布料网格应使用四边面构成，这是 Unity 布料模拟的标准拓扑前提。 影响：这三项网格要求意味着布料必须在建模阶段提前规划，后期随手拿现成模型加 Cloth 往往行不通；相比之下 PhysBones 对网格没有任何特殊要求，接入成本低得多——这也是 Cloth 只在真正需要面料级效果时才值得使用的另一个原因。

Cloth 碰撞器配置规则：仅支持 Capsule/Sphere 碰撞器、双球成锥且必须勾选 Is Trigger

结论：为 Cloth 配置碰撞时只能使用 Capsule Collider（胶囊碰撞体）和 Sphere Collider（球形碰撞体）两类碰撞器；两个 Sphere Collider 组合放置时会自动形成锥体碰撞（这是一个隐藏功能）；并且所有参与布料碰撞的碰撞体都必须勾选 Is Trigger，否则布料会穿模，角色还会原地打转。 配置要点：

  1. 碰撞器类型白名单：只有 Capsule 和 Sphere 两种可用，Box Collider 或 Mesh Collider 不在支持范围内，需要包裹肢体时优先用胶囊体近似。
  2. 双球成锥：把两个 Sphere Collider 组合起来可以模拟出锥形碰撞区域，适合做裙摆内部由粗到细的腿部碰撞体，不必依赖胶囊体。
  3. Is Trigger 必勾：漏勾 Is Trigger 时碰撞体会以实体方式参与物理，典型症状就是布料穿模加上角色转圈，属于最常见的配置错误。 关联说明：PhysBones 侧的警告阈值与抓取参数 API 记载于另一文档 avatar-dynamic-bone-limits.md 第 9 节。【证据说明】本节为 yexcadocs 社区实操经验补充，未逐条核对官方文档。

Trail Renderer 参数实操：AutoDestruct 自毁、Emitting 发射控制与 SetTextureScale 纹理缩放

结论：Trail Renderer 拖尾组件有三个关键参数，各自分工明确：AutoDestruct 负责一次性特效播完自毁，Emitting 控制拖尾是否继续生长，SetTextureScale 通过 Shader 调整拖尾贴图比例且比修改材质更省性能。 参数明细：

  1. AutoDestruct（自动销毁）：启用后，Trail 在时间结束后自动销毁自身，适合一次性效果，例如技能残影播放完毕后自动清理场景中的残留对象。
  2. Emitting（发射开关）：控制 Trail 是否持续发射；关闭后拖尾不再增长，用于在运行中随时冻结拖尾长度。
  3. SetTextureScale（纹理缩放）：通过 Shader 层面对 Trail 的纹理做比例调整，用于修正拖尾贴图的拉伸变形；由于不需要更换或修改材质本身，这种方式的性能优于直接改材质。 使用提醒：这三个参数的用法出自社区实操整理（yexcadocs），属于经验层面的总结；另外注意 Trail Renderer 会占用 Avatar 的材质球配额——每个 Trail 计 2 个材质球，添加拖尾前应把这笔开销一并纳入材质预算评估。

Trail Renderer 材质配额占用：每个拖尾计入 2 个材质球预算

结论：每个 Trail Renderer 都会占用 2 个材质球的配额，给 Avatar 加拖尾时必须把这 2 个材质名额计入总预算，否则容易在不知不觉中超标。 背景：材质球数量是 Avatar 性能评级的核心指标之一，原指南把这条提醒放在与粒子系统（Particle System）材质占用相同的语境下，说明拖尾与粒子共用同一套材质预算口径——凡视觉特效类组件，都要按其占用的材质数扣减 Avatar 可用的材质总额。 实践含义：

  1. 添加任何 Trail 之前，先盘点当前 Avatar 已用的材质球数量，确认剩余额度足以覆盖新增的 2 个名额。
  2. 多个拖尾按个数线性累加，例如 3 个 Trail 要预留 6 个材质名额。
  3. 额度紧张时优先考虑合并贴图、删减非必要特效，而不是放任材质超标。 数据边界：本条只给出「每个 Trail 占 2 个材质球」这一相对关系；当前版本 Avatar 材质总数的具体上限数值不在本段内容内，且该上限历史上随 VRChat 性能等级调整过，使用时应以官方最新性能文档为准。（2026-07-04 记录）

VRChat 动画优化原则：避免 fully-keyframed 全关键帧动画，砍 MMD/动作包并降低曲线精度

结论：VRChat 官方明确不建议使用完全关键帧（fully-keyframed）动画——这类 Animation Clip 的体积可以变得非常大，是 Avatar 包体中经常被忽视的大小来源。 官方依据：VRChat 2024-03-14 的 Dev Update 原文写道 “Don’t use fully-keyframed animations, these can get really large!”（不要使用全关键帧动画，它们会变得非常大）。完全关键帧指动画曲线上每一帧都记录了关键点的动画；骨骼多、时长长的全关键帧动画会让 clip 文件急剧膨胀。 四条动画瘦身原则：

  1. 避免制作或导入 fully-keyframed 动画（官方明确）。
  2. 避免向 Avatar 塞入过多 MMD 动画（社区整理）。
  3. 避免使用动作包（motion pack）——动作包通常携带大量用不到的动画，白白撑大包体（社区整理）。
  4. 降低动画曲线精度，减小 clip 体积（社区整理）。 证据分层：「勿用全关键帧动画」为官方 FACT 级论断；其余三条为社区教程（VRCD 18-vrchat-CI4 动画方面章节）配套的实操建议，方向与官方口径一致但并非官方原文。

Unity 动画压缩怎么选：Keyframe Reduction 与 Optimal 对比、动画数据量原理与推荐工具

结论：Unity 动画压缩首选导入设置里的 Optimal 模式，再配合 AAO/VRCFury 工具链做 Animator 级优化。

数据量原理：一帧 N 个信息就占 N 份空间；动作动画（如手臂从大腿举到头顶）的占用由浮点小数精度决定——15°、16.98°、78.24° 这样的值每帧都存储；完全关键帧+无补间 = 巨大占用。VRChat 官方也明确建议 “Don’t use fully-keyframed animations, these can get really large!”

Unity 内置压缩选项（完整文档见 Unity Manual class-AnimationClip）：

选项 作用 推荐度
Keyframe Reduction 减少冗余关键帧 三星
Optimal 根据阈值自动减少冗余关键帧 五星 推荐

推荐工具：AAO Trace And Optimize（自动 Animator 优化）、VRCFury Actions 系统（模块化动画）、Unity 内置 Animation Compression（AnimationClip 导入设置）。适用版本口径：Unity 2022.3。

Animator 有开关物件动画时 AAO 会跳过 Skinned Mesh 合并：先清理简化 Animator 再优化

结论：AAO 跳过 Skinned Mesh 合并的最常见原因是 Animator 里存在开关物件的 Animation。

机制：当 Animator 中有开关物件的 Animation 时，AAO（Trace And Optimize / Merge Skinned Mesh）会主动跳过 Skinned Mesh 合并——因为合并会破坏 Toggle 的对象引用关系。

处理：在跑 AAO 优化之前，先清理或简化 Animator（删除废弃层与无用开关动画、收敛 Toggle 结构），再让 AAO 执行合并优化。

Avatar 优化事前选择原则：Android 平台衣物挑选 5 大特征与选衣策略

结论先行：Avatar 优化的第一原则是「事前选择 > 事后优化」——在动手优化之前先选对资源，事半功倍；核心原则是事前选对资源，比事后优化 10 次更有效。

1 外观简洁 低面数，减少减面负担

Unity 贴图导入设置之 Alpha Is Transparency：作用、关闭条件与 liltoon Alpha 蒙版陷阱

结论先行：Alpha Is Transparency（Alpha 是透明的）的作用是允许导入贴图中的透明部分，应与非 Opaque（透明）渲染模式的材质球配合使用；不含透明信息的贴图应当关闭它来减小体积。

何时关闭：

  • 物体未包含透明部分；
  • 已用 PhotoShop 将贴图透明部分填充为纯色（黑/白），从根源减小贴图大小。

重要警告：有些着色器（如 liltoon）使用 Alpha 蒙版制作半透明效果。遇到这类贴图时，不要改贴图的 Alpha Is Transparency 设置，而应修改贴图对应材质球的设置，否则半透明表现会被破坏。

背景：在 Texture Memory 的优化手段中，调整贴图导入设置是减小贴图体积的最直接方法（本组导入设置来源：VRCD 18-vrchat-CI4 §贴图方面 + VRChat 官方 Dev Update 2024-03-14）。

Generate Mipmaps 要不要关：33% VRAM 与 +33% 导入大小两种口径的纠正说明

结论先行：Generate Mipmaps（生成 Mipmap）的作用是生成一系列逐渐降低分辨率的贴图、按相机距离选用合适层级；是否关闭取决于你要优化 VRAM 还是导入体积——两个「33%」说的是不同口径。

数据纠正（2026-07-04）：此前流传的「+33% 导入大小」来自 VRCD 18-vrchat-CI4 的测试数据（7.1MB → 9.5MB），测的是导入大小；lilAvatarUtils 官方文档（lilxyzw，2025）则明确指出关闭 Mipmap 可减少约 33% 的 VRAM 占用。两者不矛盾，只是应用场景不同：想省 VRAM 就考虑关闭，在意包体导入大小则保持开启。

何时关闭：

  • 贴图无复杂纹理/渐变；
  • 不在意模型的远处视觉效果；
  • Quest 平台性能要求严苛。

例外：Vertex Shader 中使用的贴图（如 outline 遮罩）必须保持 MipMap 开启，否则依赖 mip 采样的顶点效果会异常。

Read/Write Enabled 让 RAM 翻倍：99% Avatar 贴图都应关闭的读写开关

结论先行：Read/Write Enabled 允许脚本访问贴图数据（ReadPixels/SetPixels/GetPixels），代价是 RAM 占用翻倍——lilAvatarUtils 官方文档原话：“Copying textures for script access doubles the RAM consumption”。纯展示用途的 Avatar 贴图 99% 都应该关闭此选项。

何时关闭：贴图不需要在脚本中读取（绝大多数 Avatar 贴图属于此类）。

何时开启：

  • 需要运行时修改贴图的功能，如 Paint、笔刷、截图；
  • 极少数特殊 Shader 需要 CPU 端采样。

来源：lilAvatarUtils 官方文档 + Unity 官方 Texture Import Settings（https://lilxyzw.github.io/lilAvatarUtils/en_US/docs/TexturesGUI.html ）。

Mip Streaming 流式加载贴图：按需加载 mip 层降 VRAM 的实验性功能（Unity 2021.2+）

结论先行：Mip Streaming（Mip 流式加载）让引擎根据相机位置按需加载 Mipmap——只加载当前可见的 mip 层级，从而降低 VRAM 消耗，特别适合高分辨率贴图。

使用须知：

  • 状态：实验性功能（来源：lilAvatarUtils 官方文档）；
  • 版本要求：需 Unity 2021.2 及以上支持；
  • 定位：作为 Generate Mipmap 之外的补充手段，用于缓解高分辨率贴图的 VRAM 压力，启用前应在目标平台上自行验证稳定性。

Unity 贴图 Format 选择：DXT5/BC3 通吃 99% 贴图、DXT1 体积减半与法线贴图禁改格式

结论先行：贴图格式（Format）的选择规则：默认 DXT5（BC3），无透明需求降级 DXT1（BC1），法线贴图永远保持 Automatic。

  • DXT5 | BC3：适用于 99% 的贴图，支持导入透明度；
  • DXT1 | BC1：不需要透明度时使用，体积比 DXT5 小一半；
  • 法线贴图（Normal）：不应更改格式，保持 Automatic——强行改动会破坏 R 通道，导致法线数据错误、光照表现异常。

Compression 压缩质量四档对比与「Normal Quality 被误译为法线质量」翻译陷阱

结论先行：Compression（压缩质量）四档的选择口诀：默认 Normal、关键 High、极限 Low、避免 None。

选项 体积 画质 备注
None 最大（甚至大于原图） 无损 完全不进行压缩
Low Quality 极小 较低 进一步压缩可选
Normal Quality 中等 良好 默认推荐
High Quality 较大 最佳 皮肤贴图等关键部位

翻译陷阱：中文版 Unity 把 “Normal Quality” 错误翻译成「法线质量」，它的实际含义是「普通质量」（此处 Normal = 普通），与法线贴图（Normal Map）没有任何关系——不要因为翻译而避开这个默认推荐档。

Crunch Compression 官方立场：只减下载不减 VRAM，除非确有必要否则不要用

结论先行：Crunch Compression（使用 Crunch 压缩）在任何情况下都应避免使用，除非你明确知道自己需要它——它只减小下载大小，完全不减小 VRAM 占用，同时增加 CPU 负担并破坏贴图质量。

VRChat 官方明确立场（2024-03-14 Dev Update 原文）：“Crunching textures may or may not help. Avoid relying on it. Crunch reduces quality and doesn’t affect uncompressed size at all. The AssetBundle compressor does a decent job at compression anyways, and finally, un-Crunching costs CPU time. As such, you shouldn’t use Crunch unless you know you need it.”

要点拆解：

  • Crunch 降低贴图质量，且对未压缩体积毫无影响；
  • AssetBundle 压缩器本身已经足够好，下载体积不靠 Crunch 来省；
  • 解压 Crunch 需要消耗 CPU 时间，运行时有额外开销。

Skinned Mesh Renderer 合并策略：可合并条件、Face 保持独立原则与无法穿脱的代价

结论先行：Skinned Mesh 合并的原则是「能跟骨架变形的都可合，唯独 Face 保持独立」：头发、身体等物件合并后 CPU 处理负担降低，Material Slots 也同步减少（同一材质球的多 Mesh 合并后按一个 Slot 计）；代价是合并后的物件无法单独开关——也就是不能做穿脱衣服之类的切换功能。

Face 特殊处理：Face 的 Blend Shape 数量通常最多，把它混进大合并反而增加负担，因此建议头发、身体等参与合并，Face 单独保留。

冲击 Excellent 评级的两个进阶动作：

  1. 把 Body 也扔进 MergeMesh；
  2. 使用 Freeze BlendShape 固定当前外观并删除 Blend Shape（以放弃表情为代价换取评级）。

AAO Merge Skinned Mesh 五步配置：Root Transform / Anchor Override / Optimize BlendShape

结论先行：用 AAO 的 Merge Skinned Mesh 组件手动合并蒙皮网格，按以下 5 步配置：

1. 在 Avatar 物件上 Add Component > AAO Merge Skinned Mesh
2. 绑定 Root Transform（通常是 Hips）
3. 设置 Anchor Override（建议用 Body）
4. 将要合并的物件拖入「添加元素」
5. 取消勾选 Optimize BlendShape（如需保留 Blend Shape）

配置要点：Root Transform 决定合并后网格的骨架根，通常绑定 Hips；Anchor Override 建议指定 Body，保证光照与 LOD 锚点稳定；第 5 步只在你想保留表情等 Blend Shape 时才需要操作——组件默认的 Optimize BlendShape 会对 Blend Shape 数据做优化删减。

Material 与 Material Slots 的区别：只有编译后 Slot 数影响评级及两条减少路径

结论先行：Performance Rank 看的是 Material Slots（材质栏位）而不是 Material（材质球文件）：前者是编译后 Avatar 上实际的材质槽数量，直接影响评级；后者只是工程资产文件计数，不影响评级。

概念 定义 影响
Material（材质球） 以文件为单位 无
Material Slots（材质栏位） 编译后实际数量 影响 Performance Rank

减少 Material Slots 的两条路径：

  1. 合并 Skinned Mesh——同一材质球的多 Mesh 合并后按一个 Slot 计；
  2. 合并材质球（Atlas 化）——使用 TexTransTool 把多个材质烘焙进一张图集。

TexTransTool Atlas 化能力边界：不直接压材质槽、必须配合 MergeSkinnedMesh 及按材质性质分组

结论先行：TexTransTool 的 AtlasTexture 能压材质球数量和 VRAM，但它不直接压缩材质槽（Material Slot）——想让评级里的 Material Slots 真正下降，必须再配合 AvatarOptimizer 的 MergeSkinnedMesh。这是 TTT 图集化最常见的认知误区。

第二条铁律：分组必须按材质性质进行（皮肤/头发/衣服/半透明/玻璃/金属各自分开），否则半透明材质会在图集上混合错误。

v1.0.1 当前的分组方法（AtlasTexture GameObject 上的组件结构）：

AtlasTexture GameObject:
├ Material Selector: 勾选要合并的材质球
├ Material Merge Group: 按性质分组（实验性→稳定）
├ All Material Merge Reference: 指定所有材质合并目标
├ Atlas Texture Size: 输出纹理大小（2 的幂）
└ Force Set Texture: 强制覆盖纹理（Quest 适配用）

版本备注：v0.10.0 后 MergeMaterial 更名为 AllMaterialMergeReference，语义更清晰。工具官网 https://ttt.rs64.net/ ，完整文档见 tex-trans-tool.md 页面。（版本基线：TexTransTool v1.0.1，2025-12-26）

TexTransTool 与 AAO 协作执行顺序：AtlasTexture → MergeSkinnedMesh → TraceAndOptimize（v0.9.0+ API 协作）

结论先行：TexTransTool 与 AAO（Avatar Optimizer）组合使用时执行顺序是关键，固定为：TTT AtlasTexture → AAO MergeSkinnedMesh → AAO TraceAndOptimize。

执行顺序（关键）：
1. TTT AtlasTexture（图集化、合并材质球）
2. AAO MergeSkinnedMesh（合并 Mesh + Material Slot）
3. AAO TraceAndOptimize（最终优化）

深度协作机制（v0.9.0 起，通过 API 实现）：

  • AAO RemoveMeshBy* 删除的区域不会分配图集空间，避免给看不见的面浪费图集像素；
  • AAO 向 UV1 写入 UV 时，TTT 通过 API 获知改写位置并同步处理。

这意味着两个工具需要在 NDMF 工具链中按序生效；乱序执行可能导致图集空间浪费或 UV 错位。

Avatar 材质 Render Queue 三阈值规则：<2500 天空盒冲突、≥2501 失焦无阴影、≤2450 擦除材质

结论先行：Avatar 材质的 Render Queue 有三个关键阈值，配置错误是 Avatar 渲染异常的常见根因：透明材质的安全值是 2501，低于 2500 会与天空盒冲突，低于等于 2450 会擦除其他材质（破坏性 Bug）。

三阈值总览：

Render Queue 范围 行为 风险等级 典型症状
< 2500（含透明材质） 与天空盒渲染顺序冲突 中 透明物体在天空盒后面、显示异常
≥ 2501 失去焦点 + 无法接收阴影 中 半透明物体模糊、投影丢失
≤ 2450（透明材质过低） 擦除其他材质 高 整个 Avatar 的部分材质被擦除

规则 1：透明材质 < 2500——官方原文：“If a material that includes transparency is set to less than 2500, rendering problems may occur when it overlaps with the skybox.” 根因：Render Queue < 2500 会被 Unity 当作「不透明」队列、在天空盒之后渲染；症状：户外场景中透明部分显示在天空盒「后面」。解决方案：将透明材质的 Render Queue 设为 2501（Unity Transparent 标准）。

规则 2：Render Queue ≥ 2501——官方原文：“If it is set to 2501 or more, the lens effect will cause the material to lose focus and it will not be able to receive shadows.” 根因：Transparent 队列的材质不参与深度写入；症状：失去焦点（虚化效果失效）、无法接收其他物体的阴影。影响：通常这是正确的表现，除非你需要透明材质接收阴影。

规则 3：Render Queue ≤ 2450（严重 Bug）——官方原文：“If a transparent material is set to an excessively low value (such as 2450 or less), it is very likely to cause problems with other materials being erased.” 根因：过低的 Render Queue 导致 Z-test 异常；症状：其他材质被「擦除」（视觉上消失）。这是破坏性问题，必须立即修复：将 Render Queue 调整到 2501（标准透明）或 3000+（特殊效果）。
