Unity/VRChat 性能基准测试 — 组件帧时间实测（动画层/Constraints/Contacts/Cloth/PhysBones）

结论：该基准（VRCLibrary - Unity/VRChat Performance Benchmarks，原作者 JustSleightly，中文翻译 LIII Works，数据仓库 github.com/jell

知识库 avatar

性能基准测试方法论：逐步添加组件拟合成数学公式推导开销，测试环境为 Ryzen 7 5800X + RTX 4090 台式机

结论：该基准（VRCLibrary - Unity/VRChat Performance Benchmarks，原作者 JustSleightly，中文翻译 LIII Works，数据仓库 github.com/jellejurre/UnityBenchmark）收集数据的方法不是只测单个组件，而是逐步添加更多组件，从数据中推导出性能消耗的数学公式（community-tested）。

做法示例：想知道在 FX 控制器上增加一个额外动画层会增加多少帧时间，就设置 1 层、8 层、64 层、256 层四个梯度，绘制图表，把数据拟合成一条线，再用线的公式计算「再增加一层」所需的帧时间。

测试环境：CPU AMD Ryzen 7 5800X；内存 DDR4 2x16GB 3200MHz CL18；GPU NVIDIA GeForce RTX 4090。

使用边界：本页所有绝对帧时间数字都以这台高配台式机为参照口径，低端设备上的绝对值会不同；跨硬件对比时应看比例与档位关系而非照搬 ms 数值。[UNKNOWN] 拟合公式的原始数据点与回归系数未在页内给出。

帧时间预算：90fps=11ms（Quest 标准）、60fps=16ms（PC 标准）、40fps=25ms（低性能设备），1ms 占 90fps 预算约 9.1%

结论：帧时间预算表给出三个目标档位（community-tested）：90 fps = 11 ms（Quest 标准）；60 fps = 16 ms（PC 标准）；40 fps = 25 ms（低性能设备）。

换算示例：某个操作消耗 1ms，约占 90fps 预算的 9.1%。

使用方法：以目标平台的档位作为分母评估单项开销占比——Quest 内容用 11ms、PC 内容用 16ms——不要混用档位分母；单项组件的 ms 开销乘以数量后与预算比较，即可判断是否可接受。单位为 ms/帧。

动画控制器基准前提：任一动画层含状态行为使所有控制器运行时间 +50%；Animator 性能不线性缩放

结论：动画控制器基准测试的所有用例都不包含状态行为（State Behaviour），并测得两条前提规则（community-tested，页版本 1.0）：

  1. 只要一个控制器的任意动画层上有一个或多个状态行为，所有控制器的运行时间就会增加 50%。由于默认的 Action & Gesture 层中包含状态行为，这种额外开销可能出现在每一个使用的 Avatar 上。
  2. Animator Controller 的性能不会线性缩放：两个拥有 100 个动画层的 Avatar 并不会比一个拥有 200 个动画层的头像更慢。

适用条件：估算动画层数量对帧时间的影响，或比较多层少控制器与少层多控制器两种结构时，必须先套用这两条前提。[UNKNOWN] 50% 增量对状态行为类型/数量的具体依赖关系未细分。

双状态切换基准：被动切换约 +0.01ms/层，主动频繁切换比被动高 20-30%，与快速参考表数值自洽

结论：双状态（two-state）切换是动画控制器的参考基准（community-tested）：被动切换（无主动切换）每增加 1 层的额外开销约 0.01 ms；主动频繁切换比被动高 20-30%。

自洽校验：与快速参考表对照——被动约 10ms/1000 层、主动约 12-13ms/1000 层——0.01×1000=10ms，+25% 落在 20-30% 区间内，两处数据一致。

使用注意：该基准不含状态行为；实际 Avatar 因默认 Action & Gesture 层含状态行为，需在此基础上整体 +50%（见基准前提块）。单位为 ms/层。

AnyState 规则：切换数量无显著影响，启用『可以过渡到自身』即使不切换也固定 +20% 开销

结论：AnyState 行为的性能影响分两点（community-tested）：

  1. AnyState 切换数量对性能无显著影响。
  2. 启用「可以过渡到自身」（Can Transition To Self）带来约 +20% 开销，且即使根本不进行任何切换也生效——这是常驻成本。

适用条件：在 Animator 中使用 AnyState 机制，或决定是否勾选「可以过渡到自身」时。

推论：可以用 AnyState 减少过渡连线数量而不必担心切换次数本身；但应检查「可以过渡到自身」是否被勾选——不需要时应关闭，避免无谓的常驻 +20%。例外：关闭该选项即不产生此开销。

Direct Blend Tree 优化效果：1D Blend Tree 约减 75% 帧时间，默认动画层+Direct BT 约减 80%；除频繁切换场景外仍建议双状态

结论：相对双状态设置的帧时间减少幅度（community-tested）：

设置方式 帧时间减少 说明
1D Blend Tree（多个子项） 约 -75% 较慢但简单
默认动画层 + Direct BT 约 -80% 比 1D 再减少约 50%

场景建议：除非是面部追踪等频繁切换场景，否则源页建议继续使用双状态设置——Direct BT 的收益主要来自减少活动层/过渡负担，适合稳定状态的动画表现；频繁切换场景用其他方案更稳。

关联：VRCFT 面部追踪用例的实测对比见 VRCFT 控制器块，Blend Tree 版方案在参数密集且切换固定的场景收益显著。

VRCFT 控制器对比（37 个面部追踪参数）：普通版 0.1733ms，VRCFTGenerator（Blend Tree 版）0.066ms，优化 -62%

结论：37 个面部追踪参数用例下两种 VRCFT 控制器的实测帧时间（community-tested）：普通 VRCFT 控制器 0.1733 ms；VRCFTGenerator（Blend Tree 版）0.066 ms，优化幅度 -62%。

适用解读：对面部追踪这类参数密集但状态切换相对固定的场景，Blend Tree 版方案收益显著；这也与「除频繁切换场景外倾向双状态/Direct BT」的整体结论相互印证。

使用边界：这是单一用例（37 参数）的绝对值，受测试环境 RTX 4090 影响；换用参数规模或硬件时应按比例估算。[UNKNOWN] VRCFTGenerator 的具体实现与参数配置未在页内展开。

动画控制器无显著影响因素清单：每层状态/过渡数量、遮罩、子状态机、嵌套 Blend Trees、WD Off（Direct BT）几乎不影响性能

结论：动画控制器「其他发现」中，以下因素经实测无显著影响（community-tested）：

  • 每层状态/过渡数量——例外：单状态超过 1000 个布尔过渡时，1000 个过渡需要 1ms。
  • 遮罩（Mask）——无显著影响。
  • 子状态机——无显著影响。
  • 嵌套 Blend Trees——几乎无影响。
  • WD Off（Direct BT 场景）——无显著影响。

优化指向：调整动画控制器结构时不必优先考虑遮罩/子状态机/嵌套 Blend Tree 这类纯结构项；应聚焦有实测差异的项——状态行为存在与否、总层数、Direct BT 采用与否、本地 Avatar 参数数量（见显著影响因素块）。各因素单独评估，组合叠加效果未量化。

动画控制器显著影响因素：骨架使每层帧时间较无 Avatar 减少 ~50%、WD Off（动画层）+50%、本地 Avatar 参数每 1000 个 +1.5ms

结论：动画控制器「其他发现」中三个因素有实测显著影响（community-tested）：

  1. 人形/非人形骨架 vs 无 Avatar：存在 Avatar 骨架时每层帧时间比无 Avatar 基准减少约 50%。
  2. WD Off（动画层场景）：帧时间 +50%——这与状态行为带来的 +50% 是两个独立增量，可同时发生。
  3. 本地 Avatar 参数：每 1000 个参数 +1.5 ms；远程 Avatar 不适用此项。

共同特征：三者都是「增加实际计算内容」的因素，与遮罩/子状态机等纯结构项形成对照，优化时应优先处理。注意本地 Avatar 参数的 +1.5ms/1000 在 Contacts 一节同样出现，预算 Avatar 参数总量时按同一杠杆管理。[UNKNOWN] 「WD Off」（Write Defaults 关闭）的技术含义源页未展开解释。

多控制器缩放规则：非线性（2×100 层 < 1×200 层）、1×100 层 ≈ 10×30 层、层数减半省约 50%——拆分大型控制器更优

结论：多控制器与总层数之间存在非线性缩放关系（community-tested）：2 个 100 层控制器的开销 < 1 个 200 层控制器；1 个 100 层 ≈ 10 个 30 层的开销；所有控制器层数减半 → 总帧时间减少约 50%。

决策条件：在决定大型动画控制器是「合并还是拆分」时使用这组规则。

原因：动画控制器性能非线性缩放，单个巨型控制器的边际开销高于多个小型控制器之和，因此拆分大型控制器比合并更优。

例外与边界：若拆分后各控制器引入额外状态行为或重复参数，实际收益可能被抵消（状态行为见 +50% 规则）；具体比例受配置影响。装配建议：动画层很多时优先拆成规模适中的控制器（如 30 层一档），而不是把层数堆进单个控制器。

Constraints 帧时间与 681 上限：启用 1~680 个约 1.7ms 缓慢上升，681+ 跳升至约 2.4ms（+41%）

结论：约束（Constraints，指 VRChat Constraints + Unity Constraints）启用总数对帧时间的影响（community-tested）：

启用约束总数 帧时间 备注
1~680 约 1.7 ms 缓慢上升
681 及以上 约 2.4 ms 跃升 41%；VRChat 将限制设为 681

单位说明：此处为总计 ms，不是每实例数值。

预算规则：681 是 VRChat 对启用约束总数的平台上限；接近上限前应主动控制约束数量，避免跨过 681 触发性能跃升。统计总数时，「禁用条件」定义的三种关闭状态的约束不计入（见约束禁用条件块）。[UNKNOWN] 681 上限的官方出处链接未在本页锚定。

约束不计入启用总数的三种关闭方式：GameObject 关闭 / Constraint 组件关闭 / Constraint 设置关闭；仅权重置 0 不算关闭仍耗性能

结论：约束组件在以下三种情况不计入总启用数（community-tested）：(1) GameObject 被关闭（Disabled）；(2) Constraint 组件被关闭（Disabled）；(3) Constraint 设置为「关闭」（Disabled）。只有处于关闭状态的约束才被平台视为未启用。

重要警告：单纯将权重（Weight）设置为 0 而不是上述三种关闭方式，约束仍然会影响性能——既不省预算也无节流效果。

正确做法：想省下约束预算时必须使用 GameObject 级或组件级 Disable，而不是把 Weight 归零；统计是否接近 681 上限时也按「是否处于上述三种关闭状态」判断，而非看权重值。

音源 Audio Source：数量即使达到 64 个上限也测不出帧时间影响；VRChat 平台限制每个角色 3 个

结论：音源（Audio Source）方面两条数据（community-tested）：Audio Source 数量无法测出帧时间影响——即使达到 64 个上限也在测量误差内；VRChat 平台限制每个角色最多 3 个 Audio Source。

预算策略：对该组件可放宽到平台上限（3 个/角色）管理，无需像 Constraints、Contacts 那样刻意压缩数量；音频成本主要不在帧时间维度，混音与响度问题另行处理。[UNKNOWN] 64 个上限的配置口径与 VRChat 3 个/角色限制的具体版本未在页内注明。

Contacts 基准：关闭状态每 1000 个 0.5ms、开启 Receivers 每 1000 个 0.75ms（+50%）；房间上限 4096 个，超出部分停止工作

结论：接触发射器/接收器（Contacts）性能数据（community-tested）：关闭状态每 1000 个 Contacts 帧时间 0.5 ms；开启 Receivers 每 1000 个 0.75 ms（+50%）。

无关因素：形状、类型、参数数量、碰撞标签对帧时间无显著差异。

附加成本与上限：本地 Avatar 参数每 1000 个额外 +1.5 ms；房间最大上限 4096 个 Contacts，超出部分直接停止工作。

预算方法：Contacts 数量一律按「房间总上限 4096」统一预算（不只是单个 Avatar 的配额——房间内所有角色的 Contacts 共享这一池子）；接收端开启会产生额外 50% 成本，不需要接收事件时保持关闭状态更省。[UNKNOWN] 4096 上限与 0.5ms/1000 的测试配置细节未展开。

Cloth 基准：≤20 万顶点每 1000 顶点 +0.2ms、超过后急剧增加；限制按整房间计，本地角色按 3 倍顶点模拟，Colliders 使帧时间翻倍

结论：布料（Cloth）性能数据（community-tested）：顶点 ≤20 万时每 1000 顶点 +0.2 ms；大于 20 万顶点后开销急剧增加。

三条注意事项：

  1. 顶点限制针对整个房间而非单个角色——预算按房间内所有角色 Cloth 顶点之和计算。
  2. 本地 Avatar 的 Cloth 被模拟 3 次（Mirror + Shadow Clones），本地角色实际负担需按 3 倍顶点估算。
  3. Colliders 使帧时间翻倍，且每 10 个 Colliders 每个额外 +7%。

推论：给带布料的 Avatar 做 Cross-platform 或镜像场景预算时，先按 3 倍顶点折算再加 Collider 系数，否则会严重低估实际开销。[UNKNOWN] 超过 20 万顶点后的增长曲线未给出；Colliders 测试配置未展开。
